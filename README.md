# Web-Kakao

기존 카카오톡 계정의 대화방·메시지를 브라우저에서 조회하고 실시간으로 수신·대화하는 로컬 웹 클라이언트 연구 프로젝트다. 별도 채팅 서비스가 아니라 실제 카카오톡 계정과 기존 대화를 연결한다.

**2026-10-18 기준: Phase 3 진행 중, 로컬 사용 범위에서 조건부 진행.** 일반 텍스트·조회·수신과 build7 읽음에 이어, **A형 화면에서 QR·로그인, 라이트/다크 모드, 사진 발송·수신 기기 표시, 답장 전송·수신 기기의 답장 표시를 사용자가 확인했다.** 사진 업로드가 다소 느리다는 보고는 성능 개선 항목으로 남아 있다. 확인한 사례 범위의 성공이며 모든 방·첨부 형식·장시간 동작을 보장하지 않는다. **오픈채팅 텍스트도 확인한 방에서 작성·모바일 카카오톡 도착을 사용자가 확인했다.** 오픈채팅 사진·답장·읽음은 별도 미확인이다. APK 분석과 합성 결과, 실제 사용자 확인을 구분한다.

## 사용 구조와 범위

```text
이 노트북의 브라우저 ↔ 이 노트북의 Node 서버 ↔ 카카오톡 서버
     127.0.0.1:8787
```

- Windows용 카카오톡 앱, 원격 데스크톱, 휴대폰 앱을 상시 실행하는 브리지를 사용하지 않는다.
- 최초 QR 로그인과 기기 승인에는 휴대폰 카카오톡이 필요하다. 현재 사용자의 승인 기기는 iPhone이다.
- 로그인 후 휴대폰 전원을 끈 상태에서 연결·조회를 120초 확인했다. 장시간 유지·세션 갱신까지 검증한 것은 아니다.
- 사용 중에는 이 노트북의 서버가 켜져 있어야 한다. 노트북을 끄면 웹도 종료된다. 외부 공개·터널·별도 상시 서버는 현재 범위에 포함하지 않는다.
- 공식 공개 API는 일반 개인 대화방의 조회·수신·임의 방 답장을 제공하지 않아 비공식 연결을 실험한다. 카카오 로그인·나에게 보내기·조건부 친구 메시지 기능과 구분한다. [공식 메시지 API 범위](https://developers.kakao.com/docs/ko/kakaotalk-message/common)

## 최근 수정과 남은 문제

### build8 적대적 진단 보완

일반 주소 접속만으로 로컬 인증 쿠키를 얻던 경로를 닫았다. 이제 `python tools/local_web.py open`이 사용자 전용 실행 정보를 읽고 60초짜리 일회용 입장권으로 브라우저를 연다. 주소의 입장권은 즉시 제거하며 콘솔에 출력하지 않는다. 상태 조회 권한은 계정·대화 API 권한과 분리한다. 같은 Windows 사용자로 실행되는 임의 코드나 프로젝트 파일을 수정할 수 있는 프로그램까지 격리하는 기능은 아니다.

여러 탭에서 다른 방을 볼 때 폴링마다 방 진입을 반복하던 처리를 연결·방·실제 권한 세대별로 제한했다. 전경 방은 두 메시지 캐시에서 보호하며, 방 목록·설정·선택한 대화의 변경 번호를 분리했다. 메시지의 DOM을 재사용해 새 글·읽음 변경만으로 기존 사진을 다시 요청하지 않는다. 사진 캐시는 64개/30MiB이며 DNS·리디렉션·본문 수신을 합친 전체 기한과 IPv6 전환 주소 차단을 적용한다.

QR 준비의 일시적인 통신 오류는 수동 재시도 가능한 오류로 남기고, 명시적 인증 거절과 구분한다. CHATONROOM·NOTIREAD·SHIP·PING의 지정된 시간 초과는 해당 대기만 종료하며 늦은 응답을 격리한다. 실제 소켓 오류는 기존 단절 처리하고, heartbeat는 연속 세 번 실패하면 연결을 종료한다. WRITE·POST의 결과 불명 경계와 자동 재전송 금지는 유지한다. 로그인 응답과 같은 패킷에 도착하는 초기 push도 보존한다.

결과 불명 전송의 경고를 같은 서버의 대화 세션이 유지되는 동안 새로고침/새 탭에서 복원하고, 방이 목록에서 사라져도 확인할 수 있게 했다. 본문·사진은 복원용으로 저장하지 않으며 **확인**은 재전송이 아니다. 진행 중·미확인 결과는 자동 삭제하지 않는다. 완료/확인한 항목을 정리해 1,000개 한도를 회수하고, 최근 정리한 1,000개 요약을 중복 방지에 쓴다. 무기한 보존이나 새 QR 인증·서버 재시작 후 복구를 보장하지 않는다. 업로드 진단은 쓰기를 모으고 단계별 시간·바이트 요약을 별도로 보존한다. 실제 업로드 속도는 아직 측정하지 않았다.

탭이 로그인 해제 중간 상태를 놓쳐도 새 대화 세션을 구분하도록 했다. 세션이 바뀌면 화면의 이전 초안·답장·사진 준비·전송 경고·설정·알림을 비우고, 늦은 이전 응답도 버린다. 같은 세션의 수동 재연결에서는 기존 초안과 전송 확인 상태를 보존한다. 브라우저 접근 권한이 없을 때는 서버가 꺼졌다는 안내 대신 로컬 도구의 `open`으로 다시 여는 방법을 안내하며, 계정 동작을 잠그고 작성 중인 내용은 유지한다.

현재 화면은 계정별 조회·설정·알림·대화 요청에 연결 세션 표식을 붙인다. 서버는 요청을 처리하기 전과 본문 수신이 끝난 후 표식을 다시 확인하므로, 이전 세션에서 시작한 요청이 새 세션에 적용되지 않는다. 충돌하면409로 거절하고 화면 상태만 다시 확인하며 메시지를 재전송하지 않는다. 이 헤더를 생략하는 기존 직접 API 호출은 인증된 로컬 운영자 호환 동작을 유지한다. 권한 있는 운영자가 일부러 표식을 생략하는 경우까지 격리하는 기능은 아니다.

개인자료 경로와 기존 build7에서의 적용 절차는 아래를 따른다. **이번 변경은 전체 서버 재시작과 QR 재인증이 필요하다.** 사용자 서버·계정은 작업 중 조작하지 않았다. 프로젝트 폴더 ACL의 실제 교정과 기존 개인 설정 이전은 자동 수행하지 않았다.

### A형 화면과 다크 모드

`ui/a-classic.html`의 A형을 실제 앱 화면에 적용했다. 파란 대화 배경과 노란 보낸 말풍선, 정돈된 방 목록·입력창을 사용한다. 목록 상단의 달/해 버튼으로 테마를 전환하며, 계정 및 연결 설정의 **화면 테마**에서 시스템 설정·라이트·다크를 선택할 수 있다. 처음에는 Windows/브라우저의 색상 설정을 따르고, 수동 선택은 이 브라우저에 테마 문자열만 기억한다. 계정별 개인 설정 저장과 별개이며 인증·대화·사진을 브라우저에 추가 저장하지 않는다.

A형 적용과 실행 환경 보완 후 사용자 QA에서 QR 표시·로그인, 라이트/다크 모드, 사진 발송·수신 기기의 사진 확인, 답장 기능·수신 기기의 답장 표시를 **검증 성공**으로 보고받았다. 이어 별도 사용자 QA에서 오픈채팅 텍스트 작성과 모바일 카카오톡의 실제 도착도 확인했다. 에이전트의 합성 검사와 별도의 사용자 실계정 관찰이다. 앞선 사진·답장 보고에는 방 종류가 없어 오픈채팅 사진·답장의 성공으로 확대하지 않으며, 이전에 확인한 읽음 결과도 별도 이력으로 유지한다.

760px 이하에서는 대화 목록과 선택한 대화를 한 화면씩 표시한다. 대화 상단의 뒤로 버튼으로 목록에 돌아가도 작성 중인 글과 답장 선택은 유지하며, 준비 중인 사진은 취소한다. 목록 뒤의 숨겨진 대화에는 읽음을 알리지 않는다. 대화방 이름 변경은 상단 **⋯** 메뉴, 추가 이력 조회는 대화 위 **메시지 불러오기** 버튼을 사용한다. 원본 A/B/C 시안은 비교용으로 보존한다.

새 초기 테마 스크립트의 정적 경로도 추가했으므로, 이전 서버가 실행 중이면 아래 로컬 실행 절차에 따라 서버를 재시작하고 Ctrl+F5로 새 화면을 불러와야 한다. 메모리 인증이 종료되므로 QR 로그인·승인과 대화 연결이 다시 필요하다. 에이전트는 기존 사용자 서버·연결을 종료하지 않는다.

### 연결 오류와 작업 실패 분리

QR 준비의 `allowlist` 단계에서 HTTP 응답 없이 연결 오류가 나면 서버를 실행한 환경의 외부 통신 권한도 확인한다. 2026-10-17에는 에이전트의 제한된 환경에서 띄운 서버가 이 단계에서 실패했다. 같은 Node의 계정 없는 TLS 연결은 기본 환경에서 `EACCES`, 네트워크가 허용된 실행에서는 인증서 검증을 포함해 성공했다. 로그인 정보·대화 연결이 없는 실패 서버를 확인한 뒤, 네트워크가 허용된 실행에서 로컬 서버를 다시 켰다. 에이전트로 서버를 시작할 때도 실제 네트워크가 허용된 실행 모드를 사용한다. 진단·재시작 과정에서 에이전트는 QR 발급이나 로그인을 실행하지 않았으며, 이후 사용자가 직접 QR 정상 표시와 로그인 성공을 확인했다.

2차 진단에서 일반 작업의 서버 거절이 로컬 인증 전체 잠금으로 확대되는 경로와, 부가 조회의 시간 초과가 SDK 소켓을 닫는 문제를 확인했다. 안정화 수정은 연결 중 인증·등록 단계의 명시적 거절만 인증 차단으로 처리한다. 이력·텍스트·사진·읽음·방 문맥의 명시적 거절은 해당 작업의 실패로 남기고, 실제 소켓 오류나 연결 종료는 수동 재연결 가능한 단절로 처리한다. 결과를 알 수 없는 전송은 자동 반복하지 않는다.

이름·오픈링크·읽음 확인용 부가 조회는 요청 기한이 지나면 해당 대기만 해제한다. SDK의 원래 종료 타이머도 제거하고 늦은 응답을 격리하며, 실제 네트워크 오류의 종료 처리는 유지한다. 이력은 메타데이터 대기를 포함한18초 예산 안에서 다음10초 요청의 여유를 확인하고, 부족하면 확인한 부분을 반환한다. worker20초·부모22초는 바깥 안전 기한이며, 부분 이력을 최신 전체로 표시하지 않는다.

HTTP409는 작업 준비 상태의 거절로 구분하고 상태를 다시 확인한다. 이를 로컬 서버 단절로 표시하거나 텍스트·사진을 자동 재전송하지 않는다. Windows APK 추출의 합성 ADB 실행기는 한글 절대 경로를 ASCII 파일에 직접 쓰지 않으며, 사진 실험 도구의 안전 조건은 Python 최적화에서도 유지되는 명시적 검사로 바꿨다.

### 웹 발송 후 본인 모바일의 미읽음 배지

오픈채팅 텍스트 도착을 확인한 뒤, 사용자가 웹에서 보낸 글 때문에 본인 모바일 채팅 목록의 해당 방에 빨간 미읽음 배지가 표시된다고 보고했다. 모바일에서는 오른쪽의 본인 말풍선으로 정상 표시되고, 당시 웹의 읽음 동기화 옵션은 꺼져 있었다. 메시지 도착 확인은 유지하며 모바일 미읽음 상태는 별도 문제로 조사한다.

기존 송신은 WRITE `noSeen:true`, 사진 POST `ns:true`로 읽지 않고 보내는 정책이었다. 사용자는 기존 상대 메시지도 읽음 처리될 수 있다는 설명을 듣고 **직접 보낼 때는 그 방의 읽음도 동기화**를 선택했다. 현재 보완은 문자·인용 답장·사진의 명시적 발송에서 검증된 읽음 권한을 확인해 `noSeen:false`/`ns:false`를 사용한다. 별도 NOTIREAD나 추가 발송·자동 재전송은 만들지 않는다. 사진 helper의 독립 호출 기본값은 `ns:true`이며, 직접 발송 경로가 읽음 허용을 명시 전달한다.

**대화 조회 시 카카오톡에도 읽음 알리기**는 조회 동작만 제어한다. OFF인 채 단순 조회하거나 사진을 미리보기·취소하는 동작은 새 원격 읽음을 요청하지 않는다. 기존 본인 글 읽음 목표의 하향·중복 방지 경로는 이번에 바꾸지 않는다. 실제 모바일 배지가 해제되는지는 **미실행**이며 사용자 재확인이 필요하다. 송신 필드와 현상의 연관은 근거 있는 후보이지만 실제 원인을 확정한 것은 아니다.

직접 발송 읽음 보완만 적용하던 이전 차수는 **Ctrl+F5 → 계정 설정의 ‘연결 끊기’ → ‘대화 서버 다시 연결’**로 충분했다. 현재 build8은 부모 서버도 바꾸므로 아래 전체 재시작 절차를 따른다. 에이전트는 사용 중인 서버나 실제 연결을 조작하지 않는다.

### 상대방 화면의 읽음 `1`

이전 수정본에서는 상대방 카카오톡에 `1`이 남았고, 사라졌다는 초기 전달도 사용자가 정정했다. 이후 build7 보완 후의 사용자 QA에서는 **읽음이 확인됐다는 성공 보고**를 받았다. 이전 실패와 이번 성공을 구분하며 전체 방·장시간 조건을 확인한 것은 아니다.

NOTIREAD의 헤더·본문 `status0`은 요청에 대한 응답이며 상대방 화면 반영 성공을 입증하지 않는다. 실제 조회에서 요청 전후 `CHATINFO.lastSeenLogId`가 대상 위치 미만인 사례도 관측했다. 이 seen 필드와 상대방 읽음 워터마크의 의미가 같은지, 실패 원인이 무엇인지는 미확정이다.

전경·포커스·최신 메시지 표시·하단 위치·읽음 옵션을 확인한 뒤 요청한다. 과거 이력 누락이 읽음까지 막던 조건과 로컬 HTTP202를 완료로 기억하던 처리는 보완했다. 진단은 세션당 최대8개 방의 최초 읽음에서만 전후 조회하며 식별자 없이 비교 결과만 남긴다. 코드·진단만으로 성공을 판정하지 않으며, 이후 사용자 QA의 성공 보고를 별도로 반영했다.

build7은 서버 내부에서도 같은 연결·방의 CHATONROOM 성공을 먼저 확보한다. 방 진입 ACK와 멤버별 읽음 집계의 완전성을 분리하고, 검증한 응답 `o`를 해당 방의 다음 token으로 보존한다. opt0는 정수로 전송한다. CHATONROOM·CHATINFO·NOTIREAD는 제공된 방 식별자를 모두 대조하고, 식별자가 없는 응답은 정확한 요청 번호로만 받는다. 상관없는 늦은 실패 응답은 다른 방의 연결을 종료하지 않는다. 보조 CHATINFO 거부만으로 본래 읽음 요청을 막지 않으며 NOTIREAD는 유지했다. 이 변경이 기존 실패 원인을 모두 확정했다는 뜻은 아니며, 실제 읽음 결과는 후속 사용자 확인에 근거한다.

같은 화면의 여러 이벤트가 로컬 접수 직후 겹쳐도 같은 읽음 요청을 중복 제출하지 않는다. 이 중복 방지 상태와 실제 읽음 응답 상태는 별도로 관리한다. 빠른 방 전환 중 이력 조회가 HTTP409로 거절되면 새 서버 상태를 받은 뒤 마지막 선택을 조회하며, 결과가 불명확한 요청은 자동 반복하지 않는다.

### 사진 발송

후속 사용자 QA에서 미리보기 취소는 발송되지 않았고, 명시적으로 보낸 사진이 수신 기기에서 열리는 것까지 확인됐다. 이 관찰은 확인한 사진의 실제 성공이며 모든 크기·형식의 검증은 아니다.

A형 적용 후에도 사진 전송과 수신 기기의 사진 표시를 재확인했으며, 사용자는 업로드가 다소 느리다고 보고했다. 사진 크기·형식·대기 시간과 어느 단계에서 지연되는지는 아직 측정하지 않았다. 후속 성능 진단에서는 이미지 변환, 로컬 전송, 업로드 연결·파일 전송, 완료 응답 대기를 구분해 측정한다. 속도 개선을 위해 완료 확인을 생략하거나 결과가 불명확한 사진을 자동 재전송하지 않는다.

build7 이전에는 SHIP·POST 응답만 받고 COMPLETE·휴대폰 도착을 확인하지 못했다. 당시 승인된 합성 PNG6회 모두 해결을 입증하지 못했으며 마지막 시험은 소켓 쓰기262,080바이트 뒤 약19.7초에 ECONNRESET이었다. 자동 재전송하지 않는다. 기존 발송 승인은 모두 소진됐으며 추가 실발송에는 별도 대상·내용 확인이 필요하다.

build7은 SHIP/POST의 크기를 BSON Long으로 맞췄다. 단순 사진의 POST는 ex=`"{}"`, sp=null, scp=1, silence=false를 명시하고, 이 웹의 보조기기 로그인 역할에 따라 dt=4를 사용한다. 초기 정책은 ns=true였으며, 이후 사용자 선택에 따라 직접 사진을 보내는 경로는 검증된 읽음 권한을 명시 전달해 ns=false를 사용한다. 독립 upload helper의 기본값은 true다. COMPLETE의 유효 logId와 방·제공된 작성자·종류·client message ID를 확인하며 식별이 부족하거나 모순되면 결과 불명이다. 추가 WRITE를 붙이지 않는다. 이 값들이 모두 서버 필수이거나 기존 ECONNRESET의 원인이라는 증거는 없다.

업로드 도중 링크 삭제·본인 퇴장·권한 변경으로 방 상태가 무효화되면 대기를 해제한다. POST 전이면 실패로 중단하고, POST가 시작된 뒤면 결과 불명으로 남겨 자동 재전송하지 않는다.

### 방 이름과 오픈채팅

빈 이름 필드·제목 메타·참가자 이름 파싱을 보완했지만 조사 시점의 일반 단체방5개는 이름 미확인으로 남았다. 기존 목록에 있는 이름 없는 방도 CHATINFO로 보완하도록 수정했다. 최초 목록 표시 뒤 연결당 최대8개를 한 번씩 직렬 조회하며, 방 ID가 정확히 같은 응답의 제목만 사용한다. 웹 별칭은 우선하고, 멤버십·읽음 위치·이력·전송 지원은 바꾸지 않는다. 선택적 메타 오류는 건너뛰지만 실제 소켓 단절은 기존 연결 종료로 처리한다. 원래 문제가 있던 방의 실제 제목 복구와 오픈링크 이름 추가 수집은 아직 확인이 필요하다.

오픈채팅은 종류·링크 관계를 보존하고 텍스트·답장·사진·읽음의 지원 여부를 분리해 각각 검증한다. 이름을 얻어도 미확인 종류를 일괄 전송 가능으로 바꾸지 않는다.

build7은 기존 참여 OD/OM을 구분하고, 알려진 방의 링크만 제한적으로 SYNCLINK로 보완한다. 같은 방의 진입 응답·본인 멤버·알려진 역할·활성 링크를 확인한 범위에서 기능별 버튼을 제공한다. 링크·멤버 변경과 삭제는 허용 상태를 무효화하며 가입을 자동 수행하지 않는다. 오픈방 읽음에는 확인된 li를 포함한다. 역할1/2/4의 호환 해석은 고정 공개 구현에 근거하며 APK의 전체 privilege 권한표를 복원한 상태는 아니다. 조건을 충족하지 못한 방은 읽기 전용으로 남을 수 있다. 로컬 별칭은 이름 보완보다 우선한다.

후속 QA 보완은 기존 OD/OM 방의 링크 정보가 초기 동기화에서 빠졌을 때, 그 방에서 이미 확인된 링크 ID만 INFOLINK로 한 번 보완한다. 최대16개·2.5초이며 실패·알 수 없는 링크·명시 삭제/비활성은 계속 차단한다. 링크가 준비되면 방 문맥만 조회할 수 있고, 같은 방의 본인 멤버·역할을 확인한 뒤에만 텍스트·사진을 허용한다. 빈 기존 오픈방도 문맥을 요청할 수 있게 했다.

앞선 사용자 QA에서는 텍스트 불가·사진 ＋ 비활성·읽기 전용으로 실패했다. 이후 A형 화면의 별도 사용자 QA에서 오픈채팅 글쓰기와 모바일 카카오톡의 실제 도착을 확인해 **텍스트 발송을 검증 성공**으로 갱신했다. 성공한 방의 OD/OM 세부 종류·권한·개수는 보고되지 않았다. 오픈채팅 사진·인용 답장·읽음과 다른 방·권한·재연결 상황은 별도 확인이 필요하다.

## 로컬 실행

Windows x64, Python3.11 이상과 초기 다운로드를 위한 네트워크가 필요하다. Node24.21.0과 공개 후보 소스를 프로젝트의 `local-only/`에 준비한다. 전역 설치는 필요하지 않다.

아래 `python` 명령은 사용 가능한 Python 실행기를 뜻한다. 이 작업 폴더에서 확인한 번들 실행기는 `& ".\local-only\runtime\python\cpython-3.13.7-windows-x86_64-none\python.exe" -B -X utf8`이다. 시스템에 `python` 명령이 없다면 이 실행기로 바꿔 사용한다.

서버의 `start`와 브라우저의 `open`은 같은 Windows 사용자 계정에서 실행한다. 다른 계정으로 실행하면 개인자료 경로·소유자가 달라 입장 정보를 공유하지 않는다.

```powershell
python tools/prepare_node_spike.py
python tools/fetch_source_spike.py modern
python tools/fetch_source_spike.py legacy
python tools/prepare_spikes.py --install-dependencies
python tools/local_web.py start --gap-probe --messaging
python tools/local_web.py open
```

1. `python tools/local_web.py open`으로 브라우저를 연다. 기본 주소는 `http://127.0.0.1:8787`이지만 새 브라우저에서는 주소만 입력해 계정에 접근할 수 없다. 입장권이 담긴 주소나 실행 정보 파일은 공유하지 않는다.
2. **QR 로그인 시작** → 휴대폰 카카오톡 스캔·승인 → **대화방 불러오기**를 진행한다. QR·확인번호·토큰을 저장소나 채팅에 공유하지 않는다.
3. 방을 선택하면 이력을 불러온다. 추가 조회는 상단 **메시지 불러오기**를 사용한다.
4. 지원되는 일반 방에서 텍스트를 입력한다. Enter는 전송, Shift+Enter는 줄바꿈이며 한글 조합 중 Enter는 전송하지 않는다.
5. 메시지의 마우스·우클릭 메뉴에서 **답장하기·복사**를 선택한다. 키보드는 메시지 포커스 후 Shift+F10 또는 메뉴 키, 화살표 이동, Escape 닫기를 지원한다.
6. 목록 상단의 달/해 버튼으로 테마를 바꾼다. **계정 및 연결 설정 → 화면 테마**에서 시스템 설정을 다시 선택할 수 있다. 좁은 화면에서는 방을 선택해 대화를 열고 **‹**로 목록에 돌아간다.

`--gap-probe`는 SYNCMSG가 알려진 최신 범위에 못 미치면 같은 방·같은 범위의 MCHATLOGS를 한 번 확인한다. 명시적 방 ID가 일치하는 응답만 수용한다. 클릭당 최대8묶음·표시50개 제한이 있으며 전체 이력을 보장하지 않는다. `--messaging`이 있어야 전송·읽음 요청을 제공한다.

```powershell
python tools/local_web.py status
python tools/local_web.py stop
```

진행 중인 인증·연결이 있으면 stop은 거부된다. 먼저 웹의 **로컬 세션 지우기**를 사용한다. 로컬 세션 삭제·서버 종료는 원격 로그아웃과 다르다. 이전 실험 기기 SM-T733이 남아 재등록을 막는 경우, 해당 실험 기기임을 확인한 뒤 그 기기만 직접 로그아웃한다.

현재 소스 버전은 build8이고 실험 접속 프로필은 Android 태블릿 SM-T733/Android14/앱26.1.2, 보조기기 역할이다. 승인 휴대폰의 OS와는 별개다. 서버가 등록·인증을 거부하면 중단한다. 카카오 서버의 HTTPS·LOCO 통신과 브라우저의 loopback HTTP를 구분하며 외부 공개용 HTTPS 서비스는 구성하지 않았다.

**실행 중인 build7에서 처음 갱신하는 경우:** 웹의 계정 설정에서 **로컬 세션 지우기**를 누르고 다음 순서로 진행한다. `stop --legacy`는 이전 build7의 정상 종료만 허용하며 활성 인증·연결이 있으면 거절한다. 메모리 인증이 끝나므로 새 화면에서 QR 로그인·승인을 다시 수행한다. 에이전트는 기존 서버를 종료하지 않았다.

```powershell
python tools/local_web.py stop --legacy
# 기존 별칭·고정·읽음 옵션을 이전하려면 새 서버를 처음 시작하기 전에만 실행한다.
python tools/local_web.py migrate-preferences --source ".\local-only\preferences"
python tools/local_web.py start --gap-probe --messaging
python tools/local_web.py open
```

기존 개인 설정을 쓰지 않았다면 `migrate-preferences`는 생략한다. 이전은 모든 서버가 종료되고 목적지가 없을 때만 허용하며 HMAC 식별키와 설정을 함께 복사한다. 원본은 남기며 기존 OneDrive 복사본·클라우드 이력 정리는 별도다. 손상된 실행 정보나 점유된 포트를 만나면 덮어쓰거나 강제 종료하지 않고 중단한다. 이후 build8 종료는 일반 `stop`을 사용한다. 소스 갱신 뒤에는 Ctrl+F5로 화면을 새로 불러온다.

## 사용자 QA와 회귀 확인

실제 계정 검사는 사용자가 직접 진행한다. 개인정보 없는 시험 내용과 동의한 상대 또는 본인의 시험방을 사용한다. 카카오톡 PC·휴대폰의 같은 방을 동시에 열면 다른 기기가 읽음을 처리할 수 있으므로 웹의 효과와 구분한다.

이미 사용자에게서 QR·이력, 읽음, 사진 취소·실수신 성공과 로그아웃/로그인 후 섞임·중복 없음 확인을 받았다. 아래는 회귀 확인과 남은 기능의 절차다. A→B→A는 계정이 아닌 서로 다른 대화방 전환이다.

1. **연결·방 식별:** `local_web.py open`으로 연 화면에서 QR 인증과 대화방 불러오기를 진행한다. 일반방·기존 오픈방의 제목과 이력을 대조하고, 웹 별칭을 설정했다면 유지되는지 확인한다. 인증/기기 등록 거부가 나오면 반복하지 않고 오류 코드만 기록한다.
2. **읽음:** 읽음 옵션을 끈 상태에서 시험 상대의 새 글을 확인해 기준을 잡는다. 옵션을 켜고 같은 일반1:1 방을 명시적으로 선택해 최신 글이 보이도록 맨 아래에서 포커스를 유지한다. **상대방의 같은 메시지 `1`이 사라져야 통과**다. 다른 탭·다른 방·검색·사진 모달에서는 새 읽음 통보가 없어야 한다.
3. **사진:** 개인정보 없는 작은 PNG/JPEG를 선택해 미리보기·수신 방을 확인한다. 취소만 하면 발송0회여야 한다. 다시 선택해 전송을 한 번 누르고 **실제 수신 기기에서 사진이 열리는지** 확인한다. 이어 필요하면128KiB보다 큰 시험 사진을 별도1회 확인한다. 결과 불명이면 수신 여부부터 확인하고 같은 사진을 연속 재전송하지 않는다.
4. **기존 오픈채팅:** 참여 중인 OD/OM 방에서 종류·이름과 버튼 상태를 확인한다. 허용된 텍스트(`QA 확인`)·인용 답장·시험 사진·읽음을 기능별로 각각1회 확인한다. 읽기 전용인 방을 억지로 허용하지 않으며, 어느 종류에서 어떤 버튼이 비활성인지 기록한다. 새 방 가입은 QA에 포함하지 않는다.
5. **잘못된 방·중복 방지:** A→B→A 전환, 답장 취소, 사진 선택 후 방 전환을 확인한다. 본문·인용·사진이 다른 방에 붙거나 한 번 누른 메시지가 중복 도착하면 실패다. 읽음 옵션을 끈 채 수동 재연결했을 때 자동 발송·읽음 통보가 없어야 한다.
6. **직접 발송의 읽음:** 조회 읽음 옵션을 끄고 시험 방을 보기만 했을 때 기존 상대 글이 원격 읽음 처리되지 않는지 확인한다. 그 방에서 직접 텍스트·인용 답장·사진을 각각 한 번 보낸 후 실제 도착과 본인 모바일 채팅 목록의 미읽음 배지 해제를 함께 확인한다. 기존 상대 글도 읽음 처리될 수 있으므로 동의한 시험 방에서만 진행한다. 다른 방의 미읽음이 해제되거나 중복 도착하면 실패다. 사진 미리보기·취소는 발송과 읽음을 추가하지 않아야 한다.

추가 안정성 확인은 두 탭에서 A/B 방을 번갈아 전경으로 두고 연결이 유지되는지, 같은 방에 머물러 새 글을 받아도 기존 사진이 깜박이지 않는지 확인한다. 결과 불명 경고가 발생했다면 새로고침 후에도 보이는지와 **확인**으로 해제되는지만 확인하고, 시험을 위해 전송을 반복하지 않는다. 아직 이 build8을 실제 계정으로 재검증하지 않았다.

결과는 항목별 **검증 성공 / 부분 성공 / 실패 / 미실행**, 방의 임시 별칭·종류, 누른 기능과 시각, 수신 화면의 결과만 남긴다. 실제 대화·사진·토큰·QR·원본 방 ID는 보고서나 저장소에 넣지 않는다. HTTP202·status0·COMPLETE만으로 실제 성공을 판정하지 않는다.

## 데이터와 설정

- 인증·메시지·사진은 메모리에서 처리한다. 실험 인증 보관 한도는1시간이며 서버 재시작 시 재인증이 필요하다. 절전 등으로 만료 타이머가 늦어져도 인증 사용 시점에 기한을 확인한다. 인증 중 관측한 시스템 시각이 뒤로 이동하면 보수적으로 만료 처리한다. 이는 카카오 서버의 토큰 만료 시간이나 세션 갱신 지원을 뜻하지 않는다.
- build8의 실행 정보·로그·진단은 `%LOCALAPPDATA%\WebKakao\<설치별 해시>\web-auth`, 개인 설정은 같은 설치의 `preferences`에 둔다. 프로젝트의 절대 경로를 정규화한 SHA-256 앞16자리로 설치를 구분하므로 폴더를 옮기면 다른 저장 위치를 사용한다. 새 디렉터리는 실행 사용자·SYSTEM·Administrators만 허용한다. 실행 정보·개인 설정을 읽을 때는 기존 파일의 소유자·ACL·링크·크기도 검증하며 실패하면 해당 동작을 중단한다. 이 경로 계산/import 자체는 파일을 만들지 않는다.
- **이 노트북에 개인 설정 저장**을 켜면 이름·고정·방별 알림·필터·읽음 옵션을 계정별로 저장한다. 설정 파일 자체 암호화는 제공하지 않으며 `identity.key`는 HMAC 식별키다. 기존 `local-only/preferences/`의 이름 등은 평문이고 새 경로로 자동 이동하거나 삭제하지 않는다.
- 저장을 끄면 해당 계정의 설정 파일을 지우고 현재 실행의 설정은 유지한다. 작성 중인 글은 브라우저 메모리에만 있어 새로고침하면 사라진다. 방 이름 변경은 웹에만 적용된다.
- **대화 조회 시 카카오톡에도 읽음 알리기**는 기본 꺼짐이다. 직접 문자·답장·사진을 보내면 이 옵션과 관계없이 해당 방의 읽음도 동기화하며, 기존 상대 메시지까지 읽음 처리될 수 있다. 조회 읽음은 build7 사용자 QA에서 확인했으며, 새 발송 정책의 실제 모바일 배지 결과는 재확인 전이다.
- 받은 사진은 허용한 카카오 CDN에서 메모리 프록시로 표시한다. 사진당10MiB·동시4개·캐시30MiB로 제한하며 원본 주소를 브라우저 메시지 응답에 넣지 않는다.
- 알림은 본문 없이 무음으로 표시한다. 차단됐다면 Chrome 사이트 설정 → 알림 → 허용 후 새로고침한다. [Chrome 공식 안내](https://support.google.com/chrome/answer/3220216?hl=ko)
- 결과 불명인 전송은 자동 재시도하지 않는다. 같은 서버의 계정 세션이 유지되는 동안 경고를 복원한다. 재발송 전에 실제 도착 여부를 확인한다.
- 절전·네트워크 복귀 때 로컬 상태를 다시 확인하고, 확인 중이거나 로컬 서버에 연결할 수 없으면 전송·사진 제출·읽음 통보를 막는다. API 요청과 응답 본문 읽기에 기한을 두어 정체 뒤 갱신을 재개한다. 복귀만으로 재로그인·대화 서버 재연결·발송을 하지 않으며, 연결이 끊겼다면 기존 수동 연결을 사용한다. 실제 복귀 후 읽음 통보는 방을 다시 선택해야 자격을 얻는다. 정상 폴링과 단순 포커스 이동은 입력 초점을 유지한다.
- 미읽음 숫자는 이 실행에서 관찰한 수신 기준이다. 읽은 항목을 회수해 새 수신 용량을 확보하며 중복 기록도 유한하게 유지한다. 드문 중복 판별 오탐·한도·재접속으로 범위가 불완전하면 partial 상태다. 장시간의 모든 수신을 빠짐없이 세는 보장은 없다.

### 프로젝트 폴더 접근 권한

진단에서 프로젝트 폴더에 일반 Users 그룹의 쓰기 권한을 확인했다. 제품과 런타임 파일을 바꿀 수 있는 권한은 개인자료 저장소와 별도로 교정해야 한다. `powershell -NoProfile -File tools/workspace_acl.ps1`은 기본적으로 현재 루트만 감사한다. 소유자 본인이 결과와 개발 도구 접근 상실 영향을 확인한 뒤 `-Apply`로 교정할 수 있으며 실제 변경 전 확인을 받는다. 자식 폴더의 명시적 권한은 별도 감사 대상이다. 에이전트 실행 계정은 폴더 소유자와 달라 실제 ACL을 변경하지 않았다. 따라서 이 환경의 ACL 문제가 해결됐다고 판정하지 않는다.

## APK 없이 진행하는 조사

현재 코드와 고정 공개 소스를 대조하고, 합성 응답·가상 시계·격리 브라우저로 방 이름과 연결 복귀 처리를 검증할 수 있다. 이 검사는 실제 상대방 읽음·사진 도착·카카오 세션의 장시간 유지를 대신하지 않는다.

2026-10-16에는 이름 없는 방 보완·인증 만료·연결 복귀 처리와 합성 QA를 완료했다. APK 없이 가능한 모든 방법을 조사·시험한 상태는 아니다. 이후 build7에서 아래 APK 근거를 반영했고 사용자 QA에서 읽음과 사진 도착을 확인했다. 오픈채팅은 처음에는 로컬 읽기 전용 차단으로 실패했으며, 후속 사용자 QA에서 확인한 방의 텍스트 발송·모바일 도착을 확인했다.

2026-10-17 분석용 Windows PC에서 **카카오톡26.8.1.5315 native x86 PE32 설치본**과 원본/복사본 SHA-256 일치를 확인했다. REA6.5.0·Ghidra12.1.4·JDK21을 로컬에 준비하고 provider/MCP doctor, 합성 함수 분석, 실제 EXE의 리소스·Ghidra import·진입점 디컴파일을 수행했다. 반복 실행용 Windows 준비·분석 도구와 합성 검사24개도 통과했다. [PC 설치본 분석 안내](tools/pc_analysis/README.ko.md)에 명령과 검증 범위를 기록한다. 실제 정적 분석은 **부분 성공**이다. 보호·패킹을 시사하는 관측과 내부 함수2개·외부 함수31개가 반환됐으며, 읽음1·사진·오픈채팅을 수정할 기능 호출 경로는 아직 확보하지 못했다. PC 프로토콜의 결과를 현재 Android 태블릿 접속 프로필에 그대로 적용하지 않는다.

## Android APK를 사용하는 조사

1. **정적 분석 준비:** 에뮬레이터에 Google Play로 카카오톡을 설치한다. APK 추출·코드 분석에는 로그인이 필요하지 않다. Windows용 PC 카카오톡 EXE는 Android APK와 별개다.

3. **REA 분석:** 실제 버전·해시·클래스·메서드·호출 경로를 기록한다. 읽음의 방 진입·본인 읽음 위치·상대방 통보 순서와 사진의 업로드 연결·프레임·완료 처리를 웹 코드와 대조한다.
4. **실행 동작 비교:** 정적 분석과 구분해 공식 앱의 읽음 반영을 확인한다. 에뮬레이터 로그인은 별도 단계이며 기존 iPhone·연결 기기에 미칠 영향을 확인하고 사용자 승인을 받은 뒤 진행한다. 타인 데이터 접근이나 보호 기능 우회를 전제로 하지 않는다.
5. **회귀 확인:** 근거 확보 → 웹 수정 → 합성 검사 → 실계정·상대방 화면 대조로 판정한다. 실제 메시지·사진 발송은 대상과 내용을 확인받는다. 서버 성공 응답만으로 해결을 선언하지 않는다.

이 Windows PC에서는 Android provider의 CLI·별도 MCP doctor와 위 카카오톡 APK의 실제 분석을 수행했다. 현재 대화 세션에 직접 노출된 REA MCP 연결은 없으므로 별도 stdio MCP subprocess를 사용했다. 실제 런타임은 설치된 Node24.18.0, 로컬 REA6.5.0, 기존 JDK21, 고정 jadx-headless-mcp0.7.1 JAR이며 경로와 해시를 비공개 실행 기록에 남겼다. 다른 provider를 포함한 전체 환경의 정상 상태를 뜻하지 않는다. 2026-10-16 이름·복귀 처리 보완에서 **Node191개(신규23개)와 격리 Chrome37개 검사 분류가 통과**했다. 만료 타이머를 실행하지 않은 시간 점프, 다른 방·손상된 이름 응답, 요청 헤더·본문 정체, 복귀 이벤트 병합, 오래된 같은 방 응답, 전송 결과 불명과 입력 초점 유지 등을 검사했다. Chrome은 개인 프로필과 분리한 임시 프로필·합성 데이터로 실행했다. 기한 검사는 실제12/30초 타이머 분류를 확인하고 시험 타이머를80ms로 줄인 합성 검사다. 실제 절전·장시간 관찰을 뜻하지 않는다.

추가 Chrome QA에서 최초 방 선택과 주기 갱신이 겹치면 이력 조회를 빠뜨리는 결함을 발견해 수정했다. 두 응답 순서 모두 이력 요청1회, 이미 불러온 방의 추가 요청0회를 확인했다. 복귀 시 자동 연결·QR·읽음·텍스트·사진 요청은 각각0회였다. 전송 결과가 불명확하면 같은 clientId로 결과만 조회하며 재발송하지 않는다. 최종 Chrome 전후 제품·Node 검사 입력33개의 지문이 같아, 해당 수정 차수에서 실제 실행한 Node191개 결과를 재사용했다. 최초 실패와 수정 후 결과를 구분해 보존했다.

앞선 내부 결함 보완은 캐시 퇴출 뒤 이력 커서, 참가자 변경 뒤 읽음 컨텍스트, 오래된 전송 응답, 미읽음 중복 기록, 모달 뒤 읽음, 재접속 이력·사진 초안 등을 다뤘다. 당시 Node168개·Chrome29분류·Python23개 결과와 이번 검사를 구분한다. 자동 검사 통과는 실제 상대방 읽음1·사진 도착·오픈채팅 지원 성공을 의미하지 않는다.

2026-10-16 검증에서는 사용 중인 서버를 재시작하거나 실계정에 재접속하지 않았다. 실제 방 이름 복구와 실제 절전·장시간 연결은 추가 확인이 필요하다. 서버 프로세스가 이미 불러온 백엔드 파일을 바꾸면 재시작이 필요하며, 메모리 인증이 종료되므로 QR 승인을 다시 받아야 한다. reader-worker 전용 모듈은 대화 연결 때 새 프로세스가 읽는다. 앞선 reader-protocol 전용 보완과 이번 manager를 포함한 안정화 수정의 적용 범위를 구분한다.

```powershell
python -m unittest discover -s tests -v
$node = '.\local-only\runtime\node-v24.21.0-win-x64\node.exe'
$nodeTests = @(Get-ChildItem .\tests -Filter '*.test.mjs' | ForEach-Object { $_.FullName })
& $node --test @nodeTests
& $node tests/reader-browser-smoke.mjs
```

Windows의 테스트 자식 프로세스·임시 폴더 ACL·Chrome 실행 권한이 필요하다. 계정 인증·실제 발송은 자동 테스트에 포함하지 않는다.

## 프로젝트 전용 하네스

설치된 `codex-harness` 플러그인0.1.0에서 스킬 번들을 복사하고 원본 LICENSE·NOTICE를 보존했다. 과거 vendor 사본과 실제 파일 해시를 비교해 구분했으며 같은 기능이라고 가정하지 않는다. 이후 Windows 의존 작업의 결과 경로를 처리하도록 프로젝트 로컬 helper의 경로 표현1곳을 수정했다. 플러그인 캐시·전역 설정은 바꾸지 않았다. 진입점은 `AGENTS.md`다.

- 역할: `harness_explorer`, `kakao_rea_analyst`, `harness_architect`, `harness_worker`, `harness_reviewer`, `harness_qa`. 기존 Phase1 역할2개도 보존했다. 부모 세션이 계획·통합·계정/엔진 사용권·판정을 맡는다.
- 스킬: 기존 `harness`와 `kakao-android-analysis`, `kakao-protocol-change`, `kakao-web-interaction`, `kakao-verification`을 `.agents/skills/`에서 사용한다.
- 자식 최대3개, 부모 모델·추론 상속, 재귀 위임 기본 금지. 역할의 읽기 전용·쓰기 소유권은 행위 제약이며 실제 부모 권한을 상속한다. 역할 TOML만으로 OS 격리나 MCP 접근을 보장하지 않는다.
- 최초 구성에서는 자식3개를 생성·재사용해 조사·설계·독립 검토·합성 QA·REA doctor·APK 미준비 사례를 점검했다. 당시 커스텀 역할이 활성 세션에 없어 빌트인 explorer/default로 대체했다. 후속 진단·수정 차수에서는 실제 커스텀 조사·설계·구현·QA·독립 검수 역할을 실행했다. 최초 구성 결과와 후속 실행을 구분해 기록한다.
- REA 자식의 기본 권한 doctor는 `spawn EPERM`으로 실패했다. 명시적으로 권한을 높인 제한된 재점검에서 CLI/JADX 범위와 별도 MCP(도구207개·프롬프트6개)가 통과했다. 현재 세션의 직접 REA MCP 연결·카카오톡 APK 분석과 구분한다.
- 최초 구성 시 Python23개·Node132개·계정 없는 Chrome 합성 검사23개 분류와 문서/원본 해시 검사가 통과했다. 해당 구성 차수에는 제품을 수정하지 않았다. 후속 내부 결함 수정은 별도 검증 기록을 따르며, 그 초기 구성 결과만으로 실제 문제 해결을 판정하지 않았다. 이후 사용자 QA 결과는 상단에 별도로 반영했다.

[운영 문서](.harness/OPERATING.md)에 배정·소유권·자원 lease·상태·인수인계 계약, [후속 계획](.harness/FOLLOWUP.md)에 **읽음1 → 사진 발송 → 방 이름 → 오픈채팅** 순서와 공개 인수인계 요약을 기록한다. 읽음1은 APK 분석 → 별도 승인된 공식 앱 비교 → 최소 수정 → 합성/로컬 검사 → 별도 승인된 상대방 화면 확인까지 계획한다. APK 추출 키트가 이미 있으면 다른 PC에서 재사용하며, 합성/시험 APK를 카카오톡 입력으로 쓰지 않는다.

다른 Codex 세션에서 재개할 때는 `AGENTS.md`와 로컬 운영·후속 계획을 읽고 실제 역할·도구 가용성을 다시 확인한다. 프로젝트 설정은 `.codex/config.toml`에만 두며 사용자 전역 설정과 플러그인 캐시는 변경하지 않는다.

다른 PC에서 정의를 복원할 수 있도록 `AGENTS.md`, `.agents/skills/` 전체(참조·스크립트·라이선스 포함), `.codex/config.toml`, `.codex/agents/*.toml`, `.harness/OPERATING.md`, `.harness/FOLLOWUP.md`만 공유한다. `.codex/`의 그 외 파일과 `.harness/`의 실행 장부·개별 보고서, `_workspace/` 통신 기록은 계속 제외한다.

clone 후 저장소 루트에서 다음 구조 검사를 실행하고, 해당 디렉터리에서 새 Codex 세션을 연다.

```powershell
python -B -X utf8 .agents/skills/harness/scripts/validate.py --project .
codex -C (Get-Location).Path
```

새 세션에는 `README.md`, `AGENTS.md`, 운영 문서와 후속 계획을 읽고 현재 역할·스킬·도구 가용성을 확인하도록 요청한다. 구조 검사와 Git clone만으로 역할 로딩·네이티브 실행·REA 연결이 검증되지는 않는다. Codex와 필요한 실행 도구는 각 PC에 준비해야 하며 전역 플러그인 캐시·로그인·기존 에이전트 대화·실행 중 세션은 복원되지 않는다. 과거 run을 공유하지 않으므로 새 plan/run을 만들며, 현재 하네스는 Web-Kakao 전용이다. 다른 프로젝트에서는 도메인 규칙과 파일 소유권을 조정한다. 현재 제품 준비 도구와 Chrome fixture는 Windows 기준이다.

## 파일 구성과 공개 제외 범위

| 경로 | 내용 |
| --- | --- |
| `experiments/local-web/` | 브라우저 화면·QR 인증·조회/수신·전송·설정·사진 처리 |
| `experiments/`의 다른 파일 | 모의 실험·초기 진단·명시적 승인 후에만 쓰는 발송 실험 도구 |
| `tests/` | 인증·권한 경계·대화·메뉴·업로드 프레임·APK 추출의 합성 검사 |
| `tools/` | 환경·런타임 준비, 서버 관리, REA 실행, APK 추출 키트 생성 |
| `tools/vendor/codex_harness/` | 참고용 하네스 helper와 원본 라이선스 |
| `docs/`, `evidence/` | 비공개 로컬 상세 보고서·실행 근거·manifest. Git에는 포함하지 않음 |
| `local-only/` | 런타임·소스 복사본·이전 개인자료·분석 대상·합성 진단·추출 ZIP. Git에는 포함하지 않음 |

`.gitignore`는 `.env`, 자격증명·키·세션·원본 캡처·APK 및 `docs/`, `evidence/`, `_workspace/`, `local-only/`를 제외한다. `.codex/`와 `.harness/`는 위에 명시한 정의·운영 문서만 선택적으로 포함한다. 공개 안내는 제외된 로컬 보고서·실행 기록에 의존하지 않는다.

준비 도구는 새 환경에서도 필요한 `evidence/` manifest를 생성한다. 당시 package-lock은 공개하지 않으므로 전이 의존성까지 완전히 고정한 재현을 보장하지 않는다. `tools/verify_artifacts.py`는 비공개 문서·근거가 있는 작업 복사본에서 사용하는 로컬 검증 도구다.

## 단계별 이력과 참고 소스

- **Phase 1:** 공식 API 조사와 QR 인증·대화 서버 로그인·방 목록62개 수신 확인. 핵심 전체 기능 검증으로 종료한 것은 아니다.
- **Phase 2:** 기존 방·중간 이력·실시간 본문 대조, 휴대폰 OFF120초, QR 재인증 없는 수동 재접속 확인. 전체 이력·장시간 운영은 남았다.
- **Phase 3:** 로컬 텍스트·인용 답장·새 메시지 배지·방 이름·목록 정리·무음 알림·설정 저장·받은 사진 보기를 확장했다. 이후 읽음·사진 발송은 사용자 확인 사례가 있으며 오픈채팅과 나머지 제한은 상단의 현재 상태를 따른다.

QR·LOCO 기반은 [tyeom/kakao-cli 고정 커밋](https://github.com/tyeom/kakao-cli/tree/8dbbd4f7ed6b42542982252250622fa351af00e9), 채널·읽음 구조는 [node-kakao 고정 커밋](https://github.com/storycraft/node-kakao/tree/8512e4699e2cd4c26516b80d38b57b2f85a6cc8a), 이력 경계는 [OpenKakao 고정 커밋](https://github.com/JungHoonGhae/openkakao-cli/tree/6ca6ea2fd05a6660c4a80c0b61b43b416653d1d5)를 참고했다. 읽음 비교에는 [agent-messenger 고정 커밋](https://github.com/agent-messenger/agent-messenger/tree/53da74427357d8dda6caf0b21d35b700948681a1)을 추가 대조했다. 다른 구현의 존재는 이 접속 프로필에서의 성공 증거가 아니다.

분석·작업 관리 참고 프로젝트는 [REA](https://github.com/morluto/rea)와 [codex-harness](https://github.com/revfactory/codex-harness)다. 외부 소스의 라이선스·고지는 로컬 준비 과정에서 보존한다.
