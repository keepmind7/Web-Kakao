작성일: 2026-10-23

## 1. 이 문서로 인계하는 것

사용자 요구와 참고 설계, 확인한 코드 경계, 새 구현의 순서와 통과 기준을 인계한다. 아직 실행 가능한 새 하네스나 구현 승인이 끝난 상세 사양은 아니다. 이번 작업에서 만든 것은 Markdown 참고 문서다.

관련 문서는 [전체 안내](README.md), [원본 심층 분석](TOSS_HARNESS_ANALYSIS.md), [도메인을 분리한 설계 제안](PORTABLE_AGENT_HARNESS_REFERENCE.md)이다.

## 2. 요구사항과 미결정 사항

### 확정된 목표

- macOS·Windows·Linux에서 사용할 수 있는 하네스를 별도 GitHub 저장소로 관리한다.
- 카카오톡으로 작업환경의 여러 에이전트를 지시한다.
- 특정 에이전트 제품이나 데스크톱 작업 화면 하나에 고정하지 않는다.
- `/대시보드`로 현재 작업과 총괄·하위 에이전트의 상태를 본다.
- 카톡 송수신이 각 OS에서 가능한지가 첫 기반이다.

### 구현 전에 결정할 사항

| 결정 | 현재 상태 | 설계에 미치는 영향 |

## 4. 권장 구현 단계

각 단계의 통과는 그 단계의 범위에만 적용한다. 앞 단계의 합성 성공을 실제 계정·다른 OS 성공으로 확대하지 않는다.

### 단계 A — 새 프로젝트 경계와 채널 계약

1. 새 저장소의 범위와 최소 런타임을 정한다.
2. 기존 소스·라이선스·외부 의존성을 확인한다.
3. 카카오 채널의 인증·수신·발신·상태·종료 인터페이스를 정한다.
4. 브라우저 UI·Windows 준비 도구·채널 통신을 구분한다.
5. 비밀정보·설정·실행 장부의 저장 위치와 제외 규칙을 정한다.

통과 기준: 계정 없는 대역으로 수신·발신·종료를 호출할 수 있고, 새 문서에 실제 지원 범위와 미실행 항목이 적혀 있다.

### 단계 B — OS별 카카오 텍스트 왕복

1. OS 공통 코드와 경로·프로세스·권한 처리를 분리한다.
2. 각 OS의 깨끗한 환경에서 준비·진단·시작·상태·종료를 확인한다.
3. 지정한 명령용 방의 텍스트를 수신한다.
4. 같은 방에 시험 결과를 한 번 회신한다.
5. 브라우저 없이 연결을 유지하고 단절·재접속을 확인한다.

실제 로그인·기기 연결 변경·읽음·메시지 전송은 대상·내용·횟수·영향을 정한 새 확인 뒤에만 수행한다. 이전 세션의 승인은 새 실험 권한으로 사용하지 않는다.

통과 기준: OS별로 휴대폰 명령 수신과 회신의 실제 도착을 확인한다. 서버 ACK나 API 수락만으로 통과시키지 않는다. 미시험 OS는 미검증으로 남긴다.

### 단계 C — 작업 접수·영속 장부·가짜 에이전트

1. 허용 방·발신자·접두사와 명령 대상을 검증한다.
2. 명령 중복키와 Task를 원자적으로 기록한다.
3. 합성 에이전트로 실행·질문·완료·실패·지연 이벤트를 만든다.
4. 재시작 뒤 접수 장부·진행 상태를 복구한다.
5. 봇 회신의 재입력, 이력 재수신, 늦은 이벤트를 주입한다.

통과 기준: 같은 명령을 재전달해도 새 Task가 중복 생성되지 않는다. 실행 결과를 모르면 `reconciling` 등 명시적 상태로 남기고 자동 중복 실행하지 않는다.

### 단계 D — 실제 에이전트 하나씩 연결

1. 지원 도구와 버전을 현재 공식 인터페이스로 확인한다.
2. 프로젝트 루트·권한·환경변수를 제한해 새 작업을 실행한다.
3. 현재 단계·도구 요청·최종 결과를 공통 이벤트로 변환한다.
4. 추가 지시·승인·중단·재개의 실제 지원 범위를 검사한다.
5. 두 번째 어댑터를 추가해 공통 계약이 특정 도구에 묶이지 않았는지 확인한다.

통과 기준: 명령에 지정한 프로젝트·내용을 실제 도구가 받았다는 관측이 있고, 상태·실패·중단이 공통 계약에 맞게 반환된다. 설정 파일 존재나 프로세스 시작만으로 통과시키지 않는다.

### 단계 E — 대시보드와 사용자 확인

1. 영속 이벤트에서 현재 작업·에이전트 상태를 계산한다.
2. `/대시보드`, `/작업`, `/확인목록`, `/중지`를 연결한다.
3. 마지막 관측 시각·기기 연결 상태를 표시한다.
4. 질문·승인 요청을 작업·시도·요청 ID에 연결한다.
5. 완료·실패·확인 필요 알림의 빈도와 회신 중복을 제어한다.

통과 기준: 상태 조회가 새 에이전트 작업을 실행하지 않으며, 기기가 끊겼을 때 오래된 상태를 현재 진행으로 단정하지 않는다. 승인 응답은 정확한 요청 하나에만 적용된다.

### 단계 F — 멀티에이전트와 여러 기기

1. 총괄·하위 에이전트 관계와 작업 의존성을 구현한다.
2. 파일·브라우저·계정·포트 등 자원의 소유권을 관리한다.
3. 실제 동시 실행 한도와 실패·부분 성공의 통합 기준을 적용한다.
4. 여러 기기를 연결한다면 기기 등록·인증·라우팅·집계를 별도로 구현한다.
5. 기기별 프로젝트 별칭 충돌과 잘못된 작업 전달을 검사한다.

통과 기준: 병렬 실행의 소유권 충돌이 차단되고, 한 작업의 실패·취소가 관련 없는 작업으로 번지지 않는다. 사용자에게 보이는 결과는 하위 작업의 실제 근거와 일치한다.

### 단계 G — 배포·업데이트·별도 레포 공개

1. 깨끗한 환경에 실제 배포물을 설치한다.
2. 설치 반복·업그레이드·설정 보존·실패 복구를 검사한다.
3. OS별 자동 검사와 별도 실제 계정 검사 범위를 문서화한다.
4. 라이선스·제3자 고지·민감정보·배포물 내용을 검토한다.
5. 사용자가 요청한 범위에서 새 레포 생성·커밋·push·릴리즈를 진행한다.

통과 기준: 새 레포의 공개 자료만으로 계정 없는 검사와 설치 진단을 재현할 수 있고, 실제 계정이 필요한 단계는 별도로 표시한다.

실제 검증 시에는 CPU·OS 버전·도구 버전·지원 제한·검증일을 별도 열 또는 연결된 기록으로 추가한다. CI는 계정 없는 지원 경계를 검증하고 실제 계정 검사는 같은 표의 다른 근거로 기록한다.

## 7. 새 GitHub 레포로 옮길 자료

### 가져갈 자료

- 이 문서 묶음과 사용자 요구사항
- 검토·작성한 공통 계약, 합성 테스트, 설치·사용·검증 문서
- 파일별 출처와 재배포 조건을 확인한 구현 코드
- 비밀정보가 없는 설정 예시와 도구별 지원표
- 원본 라이선스·고지·변경 이력

### 새로 결정하거나 확인할 자료

- 새 레포 자체의 라이선스와 패키지명
- Web-Kakao에서 가져갈 파일의 권리·제3자 코드 경계: 이번 확인한 루트 추적 파일에는 제품 전체에 적용할 LICENSE가 보이지 않았으므로, 일부 도구의 LICENSE를 전체 제품에 확대 적용하지 않는다.
- 에이전트 도구별 인증·실행 인터페이스와 실제 사용 권한
- 공개 CI에서 재현할 수 있는 합성 검사와 별도 수동 검사의 경계

### 옮기지 않을 자료

- 토큰·비밀번호·세션 키·QR·연결 기기 원본
- 실제 대화·사진·개인 설정·사용자별 실행 장부
- APK·비공개 분석 원본·로컬 브라우저 프로필
- 다른 환경의 절대경로·agent ID·프로세스 ID·과거 승인
- 원본 관리자의 비공개 문서·평가 인프라가 존재한다고 가정한 실행 의존성

현재 Web-Kakao의 제외 규칙을 완화해서 이런 자료를 공개 대상으로 만들지 않는다. 새 레포로 코드가 옮겨지더라도 원본과 선별 파일의 출처·변경 기록을 보존한다.
