# Web-Kakao 검증·개발 기록

날짜별 검증 결과와 플랫폼 이식 과정을 보존한 문서입니다. 기록 당시의 판단과 수치를 그대로 두며, 현재 사용법과 상태 요약은 [README](../README.md)를 따릅니다. 판정은 검증 성공 / 부분 성공 / 실패 / 미실행으로 구분하고, 합성 검사·로컬 통합·실계정 결과를 섞지 않습니다.

## 최적화 후 심화 QA (2026-10-25)

새 회귀8개와 플랫폼별 실행 조건을 보완하고 Python243pass/14skip(총257), Node1057pass/2skip(총1059), 격리 Chrome9종194조건, Mac mock start/status/stop을 새로 통과했습니다. 실제 임시 파일과 반복 메모리 검사도 수행했습니다. 실서버는 read-only status에서 인증 유지·대화 연결 비활성이었고, 정제 진단의 마지막 transport 종료는 이번 QA 시작 전인17:02:41 KST였습니다. 실제 재연결은 조작하지 않았습니다. 범위·정리·제한은 [심화 QA 보고서](QA_20261025.ko.md)를 따릅니다.

## macOS 구현과 검증 (2026-10-25)

Intel Mac(macOS, x86_64)에서 준비·mock 실행·격리 브라우저 검사를 통과했습니다. Apple Silicon(arm64)용 고정 Node도 추가했지만 실기기 실행은 미검증입니다. 이후 사용자 확인 하에 진행한 실계정 결과는 이 절의 아래 항목에 있습니다.

```bash
python3 tools/prepare_node_spike.py          # 공식 darwin tar.gz + SHA-256 고정
python3 tools/fetch_source_spike.py modern
python3 tools/fetch_source_spike.py legacy
python3 tools/prepare_spikes.py --install-dependencies

python3 tools/local_web.py start --gap-probe --messaging
python3 tools/local_web.py open --browser chrome   # 기본값(default)은 macOS 기본 브라우저
python3 tools/local_web.py status
python3 tools/local_web.py stop
```

- 실행 어댑터 `tools/platforms/macos.py`: 포트 소유 PID는 `/usr/sbin/lsof`, 실행 이미지는 libproc `proc_pidpath`로 확인한 뒤 HMAC 챌린지를 거칩니다. 브라우저는 `/Applications`·`~/Applications`의 Chrome/Chromium/Edge만 사용합니다.
- 개인 저장소: `~/Library/Application Support/WebKakao/<설치별 해시>` (0700/0600, Linux와 같은 POSIX 검사). 확장 ACL은 검사하지 않습니다.
- Darwin 런타임은 `.tar.gz`라서 lzma 없는 Python(pyenv 기본 빌드 등)에서도 준비됩니다. 설치는 `renamex_np(RENAME_EXCL)`로 덮어쓰지 않고 게시합니다.
- 2026-10-25 이 Mac의 결과: Python **257 통과·15 skip**, Node **1,038 통과·3 skip·실패 0**(1,041), 격리 브라우저 하네스 8종 모두 exit0, mock start→status→open(Chrome)→stop 모두 exit0. `tests/reader-browser-smoke.mjs`는 두 탭 동시 구간에서 메인 탭이 재로드되며 CDP 시간 초과로 중단되어 **부분 성공**입니다(서버 응답은 모두 0.5초 미만, 원인 미확정).
- 2026-10-25 사용자 확인 후 이 Mac에서 `start --gap-probe --messaging` 실서버로 QR 로그인 1회 성공. `status`는 authenticated·credentialInMemory·chatConnectionActive=true, attempts=1. 같은 연결에서 사용자가 확인한 결과(**검증 성공**): 방 목록·방 이름 정상, ‘메시지 불러오기’로 기존 대화 조회, 오픈단톡방 텍스트 발송의 모바일 도착, 나와의 채팅 텍스트 발송의 모바일 도착(이후 status actualMessageSent=true). Mac에서 새 메시지 실시간 수신·읽음·사진·답장·재접속은 미확인입니다.
- 2026-10-25 진단: 같은 연결이 73분간 30초 PING에 모두 응답한 뒤, macOS가 01:39:38 유휴 절전에 들어가고 01:39:55 PING 전송 실패(`transport`)로 대화 세션이 종료됨(`exitReason: session-failed`). 인증 메모리·탭 유지 연결은 남아 `phase: authenticated`, `chatConnectionActive: false` 상태. 자동 재연결은 하지 않으며 화면의 **대화 서버 다시 연결**로 재개하는 설계. 절전 후 재연결 성공 여부는 미확인.
- macOS 임시 폴더(`/var`→`/private/var` 링크)는 개인 저장소 검사가 거절하므로 관련 테스트는 실제 경로를 사용합니다.

## 이전 인계: Mac에서 재개하기 (2026-10-24)

**(10/24 기준 기록. 10/25 macOS 구현 결과는 바로 위 절을 따릅니다.)** Windows/common/Linux 분리와 WSL 검증 코드는 함께 인계하지만, Mac에서 clone/pull한 직후 기존 실행 명령이 동작하는 상태는 아닙니다. 이 차수에는 macOS 제품 구현이나 실제 계정 시험을 진행하지 않았습니다.

현재 확인한 상태:

- Windows의 기존 기능과 사용자 확인 사례를 보존했습니다. WSL은 계정 없는 전체 회귀·합성 화면 검사와 사용자가 시험한 실제 방·사람 이름·이력 조회가 성공했습니다.
- WSL 채팅 입력 차단은 `messaging: false`로 실행한 것이 원인입니다. 마지막 관측은 인증 메모리 없음·대화 연결 종료 상태입니다. 전송 옵션을 켜서 재시작하고 새 QR을 받는 후속 절차는 아직 진행하지 않았으며, Linux 실전 송수신은 미검증입니다.
- 읽기 전용인데 사진을 보낼 수 있다고 표시하던 안내를 수정했습니다. Windows 합성 화면 표적19조건과 독립 검수를 통과했지만, 이 수정의 WSL 적용·실전 발송을 확인한 것은 아닙니다.

새 Mac에서는 먼저 소스와 환경 정보만 준비합니다. 아래 명령은 카카오톡 로그인이나 메시지 발송을 시작하지 않습니다.

```bash
git clone https://github.com/keepmind7/Web-Kakao.git web-kakao
cd web-kakao
uname -m
sw_vers
python3 --version
git --version
```

이미 clone했다면 로컬 변경을 먼저 확인하고 `git pull --ff-only`로 갱신합니다. `uname -m`의 `arm64`/`x86_64`를 기록하고 Rosetta 사용 여부까지 확인해 Apple Silicon·Intel과 실제 실행 아키텍처를 구분합니다. Python3.11 이상도 확인합니다. Windows/Linux 런타임·node_modules·인증·개인 설정을 복사하지 않습니다.

다음 구현 순서는 아래와 같습니다. 아직 없는 macOS adapter는 새로 구현할 대상입니다.

| 순서 | 시작할 파일 | 해야 할 일과 통과 조건 |
| --- | --- | --- |
| 1. Mac 고정 런타임 | `tools/runtime_distribution.py`, `tools/prepare_node_spike.py` | Darwin arm64/x64의 공식 Node 배포 파일과 SHA-256을 확인해 고정. 압축 형식·링크/경로 제한·기존 설치 비덮어쓰기·경합/실패 처리를 Mac에서 검증. Linux 전용 renameat2를 그대로 사용하지 않음 |

| 4. 도구와 회귀 | `tools/cli_support.py`, `tools/fetch_source_spike.py`, `tools/prepare_spikes.py`, `tests/test_platform_*.py`, `tests/platform-*.test.mjs` | backend 준비 후 각 CLI의 Darwin 지원 범위를 명시. 기존 거절 단언을 무조건 제거하지 말고 지원/미지원 조합·오류·부작용 없음 시험 보완 |

| 6. 실제 계정 | 위 계정 없는 검사를 통과한 뒤 별도 단계 | 사용자 확인 후 QR1회·읽음OFF·기존 방/이력 조회부터 시작. 자연 수신·재접속·설정 복원과 승인된 실제 송수신을 따로 기록 |

Mac 지원은 현재 OS 거절을 제거하거나 Linux로 가장하는 방식으로 시작하지 않습니다. 현재 `prepare_node_spike.py`·`local_web.py` 실행은 지원되지 않으며, 순수 경로 계산과 시험용 Chrome 경로 후보가 있다는 사실도 실행 지원을 뜻하지 않습니다.

## Linux·WSL 이식 기록 (2026-10-23~24)

| 구성 | 필요 조건 |
| --- | --- |
| OS | Windows x64. Ubuntu WSL2 x64는 계정 없는 회귀·화면 검사 및 사용자가 시험한 실제 방·이름·이력 조회 성공. Linux 실전 송수신은 미검증. 다른 Linux 환경은 미검증. macOS(Intel)는 준비·mock·격리 브라우저 검증 성공, 실계정 미실행 |
| Python | 3.11 이상. Windows `py -3 --version`, Linux `python3 --version` |
| Node.js | 준비 도구가 OS별 고정 버전 24.21.0을 프로젝트 안에 설치 |
| 브라우저 | Windows Chrome/Edge, Linux Chrome/Chromium/Edge 탐색 구현. 외부 브라우저 사용. Linux 한글 표시에는 CJK 글꼴 준비 필요 |
| 휴대폰 | 카카오톡 QR 로그인과 연결 기기 승인에 사용 |
| 네트워크 | 최초 도구 준비와 실제 카카오톡 통신에 필요 |

Python 실행·준비 도구와 테스트는 표준 라이브러리를 사용합니다. [requirements.txt](../requirements.txt)는 이 조건을 설명하며 추가 pip 패키지는 없습니다. Node 패키지는 저장소의 잠금 파일을 사용해 따로 준비합니다. Android APK·에뮬레이터·REA/JADX/Ghidra/ADB는 선택적 분석 도구이며 일반 웹 실행에는 필요하지 않습니다.

Windows/common/Linux 모듈 구성, 소스 패키징과 WSL의 계정 없는 시험 절차는 [플랫폼 지원 안내](PLATFORM_SUPPORT.ko.md)를 따릅니다. Windows에서 만든 런타임·node_modules·개인 저장소를 Linux에 복사하지 않습니다. 다음 설치·평소 실행 예시는 기존 Windows 명령이며, Linux 명령은 플랫폼 안내에 별도로 적었습니다.

2026-10-23 사용자 WSL2 x64·Python3.14.4에서 고정 Linux Node 설치와 fix1 junction 회귀5/5를 확인했습니다. 이후 다른 같은 UID 프로세스의 FD 접근 거절(EACCES)로 막히던 검사를 보완한 fix2에서 **mock 시작·상태 확인·정상 종료가 모두 exit0**으로 성공했습니다. 대상 Node의 모든 수신 소켓 보유·파일 권한·사용자·Node 경로·HMAC을 확인하며, 다른 프로세스와의 소켓 공유까지 배제하는 검사는 아닙니다.

fix3는 실제 WSL 플랫폼 검사에서 Python 114개·Node 45개를 모두 통과했습니다. REA 시험 전제와 공개 시험 누락을 보완한 **fix5도 사용자 WSL 전체 회귀에서 Python exit0·Node 1,039개 통과/2개 건너뜀·실패 0**을 확인했습니다. mock을 포함한 5단계가 모두 exit0이며 해당 mock은 정상 종료했습니다. 실제 Node 시험 진입점 49개 전체가 전달본에 포함됐습니다. Linux Chrome 156.0.8078.47 설치 후 발견된 긴 TMPDIR의 SingletonSocket 경로 오류는 fix6에서 브라우저 전용 임시 경로를 짧게 만들어 보완했습니다. **이후 사용자 WSL의 mock 시작·상태·격리 브라우저·종료 4단계가 모두 exit0으로 통과**했고 browserExecuted=true·mockStopped=true를 확인했습니다. 여기까지는 계정 없는 headless 합성 화면 검사입니다. 실제 계정의 후속 조회 결과는 다음 문단에 구분하며, 일반 데스크톱 알림·클립보드·절전 검증은 남아 있습니다.

후속 WSL 일반 Chrome 화면에서 앱 본문의 한글 표시를 확인했고, 사용자는 실제 대화방·사람 이름·대화 이력 조회가 정상이라고 보고했습니다. 이는 시험한 조회 기능의 사용자 관찰이며 Linux 발송·실시간 수신·읽음·설정 복원 성공을 뜻하지 않습니다. 최초 조회 시험에는 `start --gap-probe`를 안내했으므로 **전송 옵션 `--messaging`의 사용 여부를 `status`로 확인**해야 합니다. 옵션을 빠뜨리면 글·답장·사진 전송이 모두 잠깁니다. 실행 중 서버에 옵션만 추가해도 교체되지 않으며, 모드 변경은 초안 보관·로컬 세션 정리·정상 종료/재시작·새 QR 승인이 필요합니다. 읽기 전용 모드에서도 사진을 보낼 수 있다고 잘못 안내하던 문구는 fix7에서 수정했습니다. Windows 합성 Chrome 표적 19조건을 통과했으며 사용자 WSL 적용·실전 전송 검사는 아직 하지 않았습니다.

아래의 사용자 확인은 시험한 사례의 결과입니다. 모든 방·권한·네트워크·장시간 사용으로 확대하지 않습니다. 이 프로그램은 카카오톡 공식 클라이언트가 아니며 일반 대화 연결은 공식 공개 메시지 API를 사용한 정식 연동이 아닙니다.

10/21에는 사용 권한 있는 로컬 Android APK **25.11.2**를 REA/JADX로 정적 분석했습니다. Android는 본인 읽음 수신(`DECUNREAD`)과 타인의 읽음을 나눠 본인의 방 미읽음 수를 갱신하지만, 웹에는 본인 읽음을 왼쪽 배지에 전달하는 경로가 빠져 있었습니다. 이 경로와 재연결 전후 기준 보존을 보완했습니다. APK와 현재 웹 접속 프로필 **26.1.2**는 버전이 다르며, 10/21 분석 차수에서는 실제 모바일 읽음 알림 도착을 관측하지 않았습니다. 이후10/22 진단 적용 후에는 위 일반1:1 한 사례에서 수신과 실제 배지 감소를 확인했습니다. Android의 전체 DB 이력과 달리 웹은 확인한 메시지만 메모리에 보관하므로, 불완전한 초기 집계의 부분 읽음은 보수적으로 남깁니다. 전체 판정은 **부분 성공**이며 다른 조건의 배지 변화는 개별 확인이 필요합니다.

### 미해결 문제·원인 조사

- **일부 대화방 제목:** 초기 조회 범위를 벗어난 이름 미확인 방을 선택할 때 추가 조회하도록 보완. 실제 제목 확보 여부는 추가 QA.
- **왼쪽 목록 안 읽음 배지:** 10/22 첫 모바일→웹 실패를 보존하며, 후속 진단 적용·새QR 후 일반1:1 한 사례는 사용자 배지 감소와 수신→본인 판별→전달→숫자 감소 처리를 확인. 최초 실패 원인은 미확정이고 다른 방·부분 읽음·단절/장시간 조건은 별도 QA. 웹→모바일의 기존 성공과 상대방1, 과거 웹 직접 진입 배지 잔존은 구분하며 기존 읽음 조건/정책은 유지.
- **선택적 LOCO 사진 업로드:** 미디어 연결이 완료 응답 전에 닫히는 원인 미확정. 기본 HTTPS 사진 발송의 성공 사례와 별도로 남은 문제.
- **Chrome 샌드박스 오류:** `0x80000003`의 저수준 원인 미확정. 일반 Windows 사용자 권한에서는 정상 표시를 확인한 상태.

### 추가 실기기 검증

- **초기 안 읽음·새 방 목록:** 로그인 직후 누락/중복 집계와 새로 활성화된 방의 자동 표시 재확인.
- **오픈채팅의 나머지 기능:** 다른 방 종류, 사진·답장·읽음, 실제 수신 기기 표시와 새로 발견한 기존 방의 링크 보강 경로 확인. 시험한 방의 텍스트 전송은 사용자 확인 완료.
- **HTTPS 사진의 예외 상황:** 방 종류별·연속/중복·재접속 후 발송, 실제 응답 유실·ACK 역전 시 결과와 사진 표시 확인. 기존 JPEG·PNG·WebP 수신 성공은 보존.
- **연결 복구·인증 갱신·설정 격리:** 절전·탭 중단·실제 네트워크 단절·인증 만료 후 복구, 환경별 설치, 다른 계정의 개인 설정 격리 확인.
- **장시간 사용:** 16시간45분 연결 유지 사례 이후의 실제 송수신과 기능별 사용 확인.
- **사진 다운로드:** 실제 저장 파일의 형식·내용 확인. 현재는 합성 검사 통과.
- **본인 퇴장 이벤트:** LEFT의 본인 식별 필드 형식 확인. 퇴장 뒤 권한 해제 누락 가능성은 아직 가설이며 재현된 결함으로 확정하지 않음.

### 지원 범위·환경 제약

- VS Code 내부 브라우저의 입장권 전달은 미지원이며 외부 Chrome/Edge를 사용.
- Windows x64의 기존 실행을 보존하며 Linux x64 glibc·WSL2 구현을 추가했습니다. 시험한 WSL의 회귀·합성 화면과 실제 조회는 성공했지만 실전 송수신은 미검증입니다. macOS는 계정 없는 검증까지 완료(실계정 미실행)했고 Windows32비트는 미지원이며 EXE/MSI 배포는 제공하지 않습니다. 모든 회사망에서의 동작은 보장하지 않습니다.
- 동영상·일반 파일·사진 묶음 전송은 현재 기능에 포함하지 않음.
- 넓은 작업 폴더 권한의 실제 ACL 교정·개인자료 이전은 미실행. 선택적 Ghidra helper는 점이 없는 분석 작업 경로가 필요.

실제 QA는 동의한 상대나 본인 시험방에서 대상·내용·횟수·영향을 정한 뒤 진행합니다. 이전 승인을 재사용하지 않습니다. 상대방 읽음은 **상대방 화면의 같은 메시지1 해제**, 본인 미읽음 동기화는 **같은 방의 왼쪽 배지 감소와 이후 새 도착 보존**, 사진은 **실제 수신 기기의 도착·열기**로 판정합니다. HTTP202·status0·업로드 완료만으로 통과시키거나 결과 불명 전송을 반복하지 않습니다.

10/21 보완과10/22 누적 진단 적용에는 위 **업데이트** 절차의 전체 서버 재시작·새 입장·QR 인증이 필요합니다. 적용 후에는 다음을 각각 확인하세요.

1. 10/22 진단 적용 후 일반1:1 한 사례의 모바일→웹 숫자 감소는 확인했습니다. 이후 자연 사용에서 다시 실패하면 현재 누적 진단으로 수신·해석·집계·화면 중 어느 경계인지 좁힙니다. 다른 방·부분 읽음·안 읽음 필터 변화와 이후 새 메시지 보존은 이번 성공과 구분해 확인합니다.
2. 웹에서 대상 방을 직접 선택하고 최신 메시지를 불러와 하단에 포커스를 둔 상태에서 로컬 배지가 사라지는지. 조회 읽음 옵션 OFF도 별도로 확인하며, 이것은 상대방 화면의 `1` 확인과 구분합니다.
3. 시험한1000명 이상 방의 이름 정상 표시 성공을 보존하며, 아직 구분해 확인하지 않은 새 작성자·추가 이력·다른 미확인 제목만 후속으로 선정합니다.
