## 수정이 필요한 경계

### D1 · P2 · 초기화 뒤 이전 읽음 설정이 다시 켜짐

`experiments/local-web/server.mjs:154`의 요청 도착 시점 보호는 방 선택과 별칭에 있다. `:278`의 전체 초기화는 별칭 scope를 폐기하지만, 일반 `/api/preferences`에는 같은 초기화 경계가 없다. `reader-manager.mjs:134`의 `updateSettings()`도 기존 profile 소유권만 검사한다.

두 탭을 모사한 독립 입장 교환 후 공유 로컬 세션으로 다음 순서를 실행했다.

1. A의 `{readSync:true}` POST를 본문 일부만 보낸 상태로 보류한다.
2. B의 전체 개인 설정 초기화가 HTTP 200으로 끝나고 `readSync:false`임을 확인한다.
3. A의 나머지 본문을 보낸다. 이전 요청이 HTTP 200으로 처리되고 `readSync:true`가 된다.

실제 HTTP 서버, 실제 reader manager, 실제 메모리 preference store를 사용했다. 외부 전송은 주입했고 worker는 EventEmitter 모형이었다. 실제 읽음 통보는 하지 않았다. 초기화 이후 의도치 않게 읽음 기능이 다시 활성화될 수 있는 코드 경계이며, 실제 상대방 화면에 읽음을 통보했다는 증거는 아니다. 같은 경로의 영구 저장 재활성화 가능성은 정적 추론으로 남기며 디스크 파일 재생성까지 확인했다고 보고하지 않는다.

수정은 일반 계정 설정의 세대를 본문 수신 전에 포착하고, 유효한 전체 초기화를 수락할 때 이전 세대를 폐기하는 방향이 맞다. 이 검사를 manager → store → 파일 게시와 메모리 반영까지 전달해야 한다. 저장한 뒤 응답만 409로 바꾸는 방법은 충분하지 않다. 초기화 이후 새로 요청한 설정은 보존해야 한다.

### D2 · P2 · 요청 전 취소된 이름 복구가 재선택에서도 막힘

`experiments/local-web/reader-session.mjs:156`의 `selectTitle()`은 CHATINFO 발송 전에 `titleAttempts`에 방을 넣는다. 이후 `:209`에서 오래된 선택의 작업을 버려도 그 기록은 남는다.

실제 reader session에 합성 전송 계층을 주입했다. 이름 없는 방 10개 중 초기 복구 8개가 끝난 후 A를 선택하고 같은 차례에 B로 바꿨다. B는 CHATINFO 1회, A는 0회였다. 이후 A를 명시적으로 두 번 선택해도 A의 요청은 0회이고 일반 제목이 유지됐다. 별도의 정상 대조에서는 동일 fixture의 A 조회가 1회 실행됐다. 두 session은 `finally`에서 닫았다.

예약과 실제 시도를 분리해 **발송 전 폐기된 작업만** 명시적 재선택에서 다시 예약하도록 수정할 수 있다. 이미 전송한 요청의 거절·timeout·오래된 응답을 자동으로 반복하지 않는 기존 계약은 유지해야 한다. 실제 계정에서 이름 실패 빈도를 측정한 것은 아니다.

### D3 · 조건부 P2 · 완료된 이력 응답이 다른 방 요청을 해소함

`experiments/local-web/reader-protocol.mjs:161`은 packetId가 맞지 않아도 첫 동명 SYNCMSG pending에 응답을 연결한다. WRITE와 달리 완료된 이력 응답의 재도착을 걸러내는 기록은 없다. `reader-session.mjs:403`에서 받은 body는 요청한 방의 `store.history()`로 전달되며, `reader-data.mjs:208`과 `:571`의 일반 이력 경로는 roomId가 없는 로그를 허용한다.

기존 시험과 같은 SDK 형태의 가짜 pending client에 실제 guard와 store를 연결했다. A의 roomId 없는 응답을 완료한 후 B의 이력을 요청하고 A의 완료 패킷을 다시 주입했다. B promise가 해소되고 A의 합성 로그 1개가 B store에 들어갔다. `requireRoomId:true` 대조에서는 같은 로그의 수용이 0개였다.

이는 **재전달을 직접 주입한 경계 재현**이다. 실제 카카오 서버의 응답 재전달, 실제 SDK 소켓부터 화면까지의 종단 실행, 실제 방 혼합 사건은 확인하지 않았다. 수정 전 현재 서버의 packetId·roomless 응답 계약을 대조해야 한다. 정상 roomless 이력을 전부 거절하는 단순 변경은 피하고, 요청별 상관관계와 완료 응답 재수용 방지를 함께 설계할 필요가 있다.

## 성능과 죽은 코드

- **방 전환 후 남은 이전 방 이력:** `reader-session.mjs:401`부터의 반복은 새 페이지를 보내기 전에 선택 세대를 다시 검사하지 않는다. A 이력 진행 중 B로 바꾸어도 A의 후속 요청이 계속돼 B가 기존 작업의 18초 예산 안에서 대기할 수 있는 구조다. 이미 보낸 응답은 A 캐시에 반영하고, 이후 A 페이지 발송만 중단하는 방안을 검토할 수 있다. 실제 사용 속도 개선 폭은 측정하지 않았다.
- **Windows 영구 설정 저장:** 폴더·키·파일을 매번 별도 Python helper로 재검사한다. 이번 전체 Node의 실제 영구 저장 64건 burst 시험은 162.720초, 두 store 병합 시험은 23.530초였다. 합성 부하 시험의 수치이며 실제 설정 클릭의 지연을 측정한 것은 아니다. 파일 보호를 생략하거나 성공 결과를 영구 캐시하는 최적화는 권하지 않는다. 검사와 쓰기를 한 트랜잭션으로 묶는 설계는 가능하지만 보호·취소·계정 소유권 회귀가 선행돼야 한다.
- **정리 후보:** `reader-session.mjs:24`, `:207`, `:220`의 `titleInFlight`는 대입만 있고 소비자가 없다. `tools/private_storage.py:13`의 `subprocess`도 모듈 내 사용과 저장소의 직접 속성 참조를 찾지 못했다. 기능 결함보다 우선순위가 낮다. macOS adapter의 POSIX 함수 import는 외부 재수출에 사용하므로 미사용 import로 삭제하면 안 된다. 전체 저장소의 죽은 코드를 모두 검출했다는 의미는 아니다.

## 별도 확인이 필요한 브라우저 검사 실패

네 탭 사진 검사는 3조건 중 2통과·1실패, 종료1이었다. 브라우저 발생 timestamp·로컬 서버·상류의 동시 요청은 모두 최대2였으며, 네 탭의 status 도착 시간은 35/41/42/177ms로 기존 기준을 통과했다. SSE와 사진 때문에 상태 요청이 장시간 대기한다는 가설은 이번 조건에서 재현되지 않았다.

실패한 단언은 모든 사진 Network 항목이 종료되고 `canceled:true`여야 한다는 조건이다. 사진8건 모두 종료 시각이 있었으나 한 탭의2건만 `canceled:false`였다. 두 건은 약76~79ms에 끝났고, 방 전환 직후 취소 POST·사진 응답 close가 관측됐다. 상류 취소8회·남은 상류 작업0개였으며 Chrome·서버 정리도 확인됐다.

수집기는 `Network.loadingFinished`와 `loadingFailed`의 종류, 오류 문자열, HTTP 상태를 보존하지 않아 두 건의 정상 HTTP 종료와 네트워크 오류를 구별할 수 없다. 취소 누락이나 timeout을 입증하는 자료는 없으며 정상 완료로도 확정하지 않는다. 브라우저 재요청이 retired409로 끝났을 가능성은 가설이다. 원래 실패를 유지하고 다음 조사에서 이벤트 종류·오류·HTTP 상태와 서버 요청 연결을 추가 관측해야 한다. 이번에는 단언·기한·제품을 바꾸거나 이 검사를 반복해 통과 결과를 고르지 않았다.

이번에는 진단만 수행했다. 제품 수정·실제 계정 회귀·다른 OS 실행·커밋·push는 미실행이다. 기존 서버를 재시작할 이유도 이번 진단에는 없다.
