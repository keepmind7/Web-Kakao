# 같은 방의 별칭 저장 역전 수정 — 2026-10-26

## 문제와 변경

기준은 `49b9997`과 앞선 미커밋 수정본이다. 독립 진단에서 **A 저장 요청의 본문 보류 → 편집 취소 → 같은 방 B 저장202 → 늦은 A 저장202 → 최종 A**를 실제 로컬 HTTP로 재현했다. 편집창 소유권 검사만으로는 서버의 오래된 쓰기를 막지 못했다.

이번에는 브라우저의 편집 순서부터 서버의 수락·저장·메모리 적용까지 연결했다.

- 새 서버는 `roomPreferenceOrdering:true`를 광고한다. 해당 광고가 있을 때만 웹의 별칭 저장/초기화가 페이지 UUID와 별도 증가 sequence를 보낸다. 구 서버에는 기존 `{room,title}`만 보낸다.
- 서버는 인증·CSRF 검사 후 본문을 기다리기 전에 reader 객체·연결 attempt·헤더 도착 순서를 포착한다. 유효한 본문을 받은 뒤 비동기 저장에 들어가기 전에 **방별 별칭 의도**를 예약한다.
- 같은 페이지·같은 방은 sequence로 역전을 막는다. 현재 최신 의도가 같은 페이지라면 더 높은 sequence는 헤더 순서가 뒤집혀도 수락할 수 있다. 다른 페이지나 기존 형식 요청은 인증된 헤더 도착 순서를 따른다. 서로 다른 탭의 실제 클릭 시각을 복원한다고 주장하지 않는다.
- 더 새 의도가 생기면 이전 `isCurrent()`가 무효가 된다. 이 검사를 `reader-manager.roomPreferences()`에서 기존 profile·방 소유권과 결합해 `profile.setRoom()` 및 화면 상태 적용까지 전달한다. 기존 파일 저장기의 큐·비동기 권한 검사·atomic 게시 직전 검사도 같은 의도를 확인한다.
- 실패·결과 불명·늦은 완료가 이전 의도를 부활시키지 않는다. 자동 재전송은 추가하지 않았다. HTTP 연결 중단을 이미 적용된 저장의 취소 성공으로 해석하지 않는다.

`title:null` 초기화도 같은 보호를 받는다. 별칭을 포함하지 않는 고정·알림 변경과 다른 방의 저장은 서로 차단하지 않는다. 순서 metadata는 파일의 별칭 patch에 저장하지 않는다.

## 전체 개인 설정 초기화의 인접 경계

독립 소스 검수에서 **별칭 A 보류 → 전체 개인 설정 삭제 → 늦은 A가 별칭을 재생성**하는 경로도 도출했다. QA의 실제 로컬 HTTP/manager 검사에서 추가4조건 중3실패로 확인한 뒤 함께 수정했다.

유효하고 인증된 초기화 요청을 수락하면 비동기 삭제 **전에** 이전 별칭 scope를 무효화한다. 삭제가 실패해도 이전 요청을 되살리지 않는다. 초기화 이후 새로 저장한 C는 새 scope에 속하며, 삭제 완료 시 scope를 다시 지워 C를 폐기하지 않는다. 잘못된 초기화 본문·CSRF는 정상 별칭 요청을 무효화하지 않는다.

## 범위와 적용

순서 watermark는 연결 범위에서 최대500방·방당128페이지를 보존하며, 조용히 오래된 항목을 버리는 대신 초과를409로 거절한다. 새 연결에서 범위를 갱신하고, 이전 본문·저장 의도는 이전 scope로서 거절한다. 기존 개인 설정의500방 제한과 별도 프로세스 간 잠금 부재는 바꾸지 않았다. 구 서버의 미광고 경로에는 새 순서 보장을 소급하지 않는다.

이번 결과는 별칭의 **합성·계정 없는 로컬 통합 검증**이다. 실제 카카오 방 제목 변경이나 실제 계정 회귀 성공으로 확대하지 않는다. 기존 사용 중인 서버·로그인은 유지했으며 재시작·QR·읽음/발송·커밋·push는 하지 않았다. 서버 모듈 적용에는 README의 초안 보관 → 로컬 세션 정리 → 서버 stop/start → open → QR 승인이 필요하다.
