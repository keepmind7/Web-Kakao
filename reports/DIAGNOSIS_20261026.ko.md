## 연결 실패·데이터 강건성

### D7. TCP 오류가 나도 SDK connect Promise는 기한까지 대기

고정 공개 SDK `tyeom/kakao-cli` 커밋 `8dbbd4f7ed6b42542982252250622fa351af00e9`의 `src/kakao/forge-protocol.ts:459–480,658`을 확인했습니다. 제품의 `guardReaderClient`는 connect를 보완하지 않고 `room-probe.mjs:48`의 error→disconnect도 해당 Promise/타이머를 정리하지 않습니다.

실제 guarded SDK를 **닫힌 임시 loopback 포트**에 연결했습니다. 180ms 기한에서 socket 오류는 약6ms에 났으나 직후 Promise는 미완료였고 약215ms에서 실패가 정착했습니다. 기본 기한10초를 실제로 기다린 실험은 아니지만, 오류 뒤 기본 기한까지 대기하는 코드 경로가 확인됐습니다. 무기한 누수라고 단정하지 않습니다.

개선은 제품 adapter에서 초기 error/close와 connect Promise·타이머·소켓을 함께 정착시키는 것입니다. 고정 공개 원본을 몰래 수정하거나 단순 Promise race로 원래 타이머를 남기지 않습니다. 이 조치는 성공한 연결의 왕복 시간을 줄이는 최적화가 아니라 **이미 실패한 연결의 불필요한 대기**를 줄입니다.

### D8. 비정상 숫자 필드가 전체 연결 종료로 이어질 수 있음

`reader-data.mjs:103,137,219` 등에서 `Number(value)`를 직접 호출합니다. BSON으로 표현 가능한 `{valueOf:0,toString:0}`를 합성 메시지 type에 넣으면 TypeError가 재현됩니다. session push의 전체 decode catch(`reader-session.mjs:323`)는 해당 예외를 연결 종료로 처리합니다.

숫자 변환을 예외 없는 공통 검증으로 정리하고, 개별 잘못된 항목의 거절과 전체 프레임 실패를 구분할 필요가 있습니다. **실제 카카오 응답이 이 형식이거나 상대가 제어할 수 있다는 근거는 없습니다.** 과거 사진 사건의 원인이나 공격 가능성을 확정하지 않습니다.

### D9. ‘초기화·삭제’ 뒤 손상 복구본 잔존

합성 설정을 손상시키고 복구 저장하면 `.corrupt-*`가1개 생깁니다. `forget()`은 true이고 현재 계정 JSON은 없어지지만 복구본1개는 남습니다(`preferences.mjs:77,95–110`). 현재 UI는 계정의 저장 파일 삭제를 안내합니다(`app.js:1120`).

복구본 보존 자체는 기존 테스트에서 의도한 동작입니다. 다만 **명시적 초기화 때 복구본도 지울지, 남긴다고 안내할지** 삭제 계약을 정리해야 합니다. 다른 계정 자료·설치 identity key를 무조건 함께 삭제하는 방식은 권하지 않습니다. `close()`가 디스크를 보존하는 것은 별개의 의도된 동작입니다.

## 연결 지연의 주요 개선 지점

### C1. 필수 연결 완료와 선택적 링크 조회 분리

`reader-session.mjs:348–362`는 LOGINLIST를 받은 뒤에도 SYNCLINK 최대4,000ms→누락 INFOLINK 최대2,500ms를 직렬로 기다리고 나서 loginlist 방 목록을 발행합니다. manager는 그 이벤트에서 연결 완료로 바뀝니다(`reader-manager.mjs:222`).

각 메타 응답을200ms씩 보류한 합성 gate에서, 첫/두 번째 gate가 닫힌 동안 loginlist 목록 발행은 없었고 둘 다 풀면 정상 발행했습니다(해당 합성 실행 약438ms). **실제 카카오 연결 지연을438ms 또는6.5초로 측정한 것이 아닙니다.** 6.5초는 두 부가 요청의 설정 기한 합입니다.

권장안은 유효 LOGINLIST로 목록·연결 상태를 먼저 공표하고, 링크 정보는 제한된 후속 작업으로 채우는 것입니다. 링크·참여정보를 검증하기 전 발송 capability는 계속 차단해야 하며, 세대·late response·초기 읽음 기준도 보존해야 합니다. worker20초·manager22초 예산을 부가 작업이 소비하는 현재 구조도 함께 정리할 수 있습니다.

### C2. 부가 정보보다 선택한 방 작업을 우선

`reader-session.mjs:380–381,453–454`는 방과 무관한 background 제목/발견 Promise를 기다립니다. 발견 작업은 CHATINFO5초와 링크 복구 최대6.5초를 같은 Promise에 포함합니다. **최대11.5초는 설정 합계이며 실측값이 아닙니다.**

이력 총예산18초 중 다음 SYNCMSG 시작에는10.25초가 필요하므로, 부가 작업에서7.75초를 넘게 쓰면 실제 SYNCMSG를 한 번도 요청하지 않는 경로가 있습니다. 기존 `reader-resilience.test.mjs`는 이 예산 방어를 검사합니다. 예산 검사를 지우기보다 foreground 우선순위와 부가 작업의 중단/재개 계약을 바꾸는 것이 맞습니다.

제목 최대8개 조회는 연결 완료 **후**이므로 첫 연결 지연에 다시 합산하지 않습니다. 다만 배치가 모두 끝나야 제목 변경을 발행해 먼저 찾은 이름도 늦게 표시될 수 있습니다.

실제 CLI와 같은 `asyncSecurity=true`·기존 합성 설정 파일이 있는 새 store에서 측정했습니다.

### C4. 사진의 논리 슬롯과 실제 HTTP·상류 작업을 구분

현재 단일 탭 합성13조건은 통과했습니다. 3탭에서는 초기 동시 사진2개·상태 조회 도착 전 대기21/29/30ms는 통과했지만, 방 전환 handoff에서 사진 응답4개가 약117ms 겹쳐 ‘항상2개’ 검사가 실패했습니다. `queueMicrotask(unlock)`은 HTML 이미지 취소 순서를 지연할 뿐 서버 close나 TCP/CDN 종료 확인이 아닙니다.

검사는 peak 단언 전까지 남은 잠금0·본인 방 전환 후 이전 큐의 재시작0·사진 요청 모두 canceled를 확인했습니다. 따라서 취소 전체 실패로 확대하지 않습니다. `maxServerPhotos`라는 기존 fixture 필드도 **열린 로컬 응답 수**이지 CDN fetch 수가 아닙니다. 관측된4개를 상류 다운로드4개로 바꿔 보고하지 않습니다. Windows/Mac 차이가 원인이라고 판단할 근거도 없습니다.

별도로 `server.mjs:114 → photos.get()`에는 HTTP 소비자 종료가 전달되지 않습니다. cache fetch는 자체8초 기한 또는 전체 clear까지 남을 수 있고40개 admission의 큐 대기 시간은 별도입니다. 실제 상류 잔존 밀리초는 이번 기록에 없습니다. 같은 URL의 여러 소비자는 보호하면서 마지막 소비자가 사라질 때 취소를 전달하는 방향을 권합니다. 논리 잠금·열린 HTTP·상류 fetch를 따로 계측해야 합니다. 고정 sleep을 늘리거나 검사/상한을 완화해 통과시키는 방식은 권하지 않습니다.

### C5. 낮은 우선순위 비용

- 방 목록 최대500개를 반복 필터/정렬하고, 한 방만 바뀌어도 전체 행 DOM을 교체합니다. manager에도 최대500² 비교가 있습니다. keyed 갱신·Set/Map 비교와 revision 기반 처리가 후보지만 실제 CPU 병목으로 측정한 것은 아닙니다.
- 이전 방 GET은 결과만 무효화하고 HTTP 취소는 기한까지 기다립니다. GET의 intent 취소를 연결할 수 있습니다. 전송 POST를 같은 방식으로 취소/재전송하면 결과 불명과 중복 위험이 있으므로 분리합니다.
- 설정의 전체 파일 읽기/직렬화·동기 fsync, 깊이에 따른 POSIX 경로 중복 검사는 측정 후 개선할 항목입니다. 기존500방·1MiB 상한을 고려해야 합니다.

## 죽은 코드와 기존 최적화

즉시 삭제해도 된다고 확정한 제품 함수는 없습니다. app의84개 함수는 동일 파일 참조가 있고, 사진 모듈은 server asset→HTML script→앱의 실제 경로에 연결됩니다. 이는 모든 동적 경로에 대한 도달 가능성 증명은 아닙니다.

- `localRequest`의 text 응답 분기는 현재 제품 caller가 JSON만 사용하므로 낮은 우선순위 정리 후보입니다. 속도/메모리 이득은 측정하지 않았습니다.

## 권장 작업 순서

### 사용자 체감 구간에 따른 우선순위

후속 사용자 답변은 기존 경험에 대한 확인이며 새 계정 실험은 아닙니다. 방 전환 성능 작업에서는 다음 순서로 좁힙니다.

1. **방 선택 수락·캐시 표시·이력 조회 분리:** `app.js:642–660`은 view 수락 뒤 로컬 페이지를 먼저 표시하고 필요한 이력을 요청합니다. 이미 불러온 방의 선택은 캐시 경로이므로 매번 카카오 이력 요청을 한다고 가정하지 않습니다. 클릭→view 수락→로컬 메시지 응답→첫 본문 DOM 표시와, 필요한 경우에만 실행하는 이력 요청의 부가 Promise 대기/실제 요청 시간을 분리합니다. C2의 부가 조회가 foreground를 막는 경로를 우선 개선합니다.
2. **이전 방 GET의 실제 취소:** 결과 무효화와 네트워크 종료를 구분하고, 빠른 전환 후 남은 조회가 현재 방 조회와 경쟁하는지 측정합니다. 현재 방의 선택 소유권·세대 검증은 유지합니다. 발송 POST를 자동 취소·재시도하는 변경은 포함하지 않습니다.
3. **현재 화면 사진 우선:** D6의 화면 밖 잠금 대기와 C4의 소비자 취소 전달을 보완합니다. 슬롯 대기→로컬 HTTP 시작/끝→상류 fetch→이미지 load/표시를 나눠, 첫 사진과 현재 화면 사진의 완료 시간을 별도로 봅니다. 공유 사진을 보는 다른 탭의 요청은 중단하지 않습니다.
4. **마지막 렌더 비용 측정:** 응답→최대50개 본문 DOM 갱신→레이아웃을 측정합니다. 메시지 DOM 재사용(`app.js:748–763`)과 사진 지연 로딩은 이미 구현돼 있습니다. 이를 미구현이라고 보고하거나 전체 렌더를 원인으로 미리 확정하지 않습니다.

비교는 동일 합성 데이터의 캐시 있음/없음·사진 있음/없음·단일 탭/다중 탭·빠른 방 전환으로 나누고, 단계별 횟수·소요 시간만 남깁니다. 실제 방 ID·본문·사진 URL은 계측 기록에 넣지 않습니다. 이번 답변만으로 새 성능 실험이나 제품 수정을 수행하지 않았으며 기존 테스트 수치도 바뀌지 않습니다.

**C1의 초기 링크 조회6.5초 예산과 C3의 Windows 설정 준비1.84초는 매번 방을 선택할 때의 원인으로 확인된 수치가 아닙니다.** 사용자 체감의 원인을 확정하려면 위 단계별 측정이 필요합니다. 다음 전체 수정 순서는 정확성·저장 보호를 포함하며, 방 전환 성능 작업의 우선순위와 구분합니다.
