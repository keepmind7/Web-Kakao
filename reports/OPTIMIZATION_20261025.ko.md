# 메모리·운영 최적화 (2026-10-25)

Intel macOS, Python 3.11.9, 고정 Node 24.21.0에서 진단 결과를 수정했습니다. 기준 커밋은 `f85453679971d61a9ddeb07aa58162cb3cd97aae`이며 변경은 작업 폴더에만 있습니다. 실제 카카오톡 계정·읽음·발송·로그인·사용 중 서버 재시작은 수행하지 않았습니다.

이 문서는 최적화 직후의 측정·검증을 보존합니다. 후속 전체 재검사·실제 파일/메모리 순환 QA와 최신 실서버 연결 관측은 [심화 QA 보고서](QA_20261025.ko.md)를 따릅니다.

## 메모리 측정

동일한 주입형 부하를 변경 전·후 각각 새 Node 프로세스에서 실행하고 GC 3회 뒤의 힙 증가량을 비교했습니다. 개인 대화·실제 사진·카카오 서버는 사용하지 않았습니다.

| 합성 부하 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| 70B 사진 20,000장, 각 URL에 3,500자 경로: 유지된 JS 힙 증가 | 78,533,072 B (74.90MiB) | 2,030,080 B (1.94MiB) |
| 보안 검사를 보류한 설정 호출 10,000회: 유지된 JS 힙 증가 | 9,715,928 B (9.27MiB) | 117,160 B (0.11MiB) |
| 보류 중 설정 작업 수 | 10,000 | 64 |
| 즉시 명시 거절된 설정 요청 | 0 | 9,936 |

이는 긴 URL을 가진 작은 사진과 느린 보안 검사라는 **합성 조건의 유지 메모리**입니다. 일반 사용의 전체 RSS·Chrome 메모리·처리 속도에 대한 절감률을 의미하지 않습니다. 사진 캐시를 지운 뒤 힙 증가량은 전후 모두 약 0.02MiB로 돌아왔고, 설정 부하는 profile을 닫은 뒤 검사를 해제해 파일 생성 없이 전부 종료했습니다.

재현 명령(프로젝트 루트, OS에 맞는 고정 Node 사용):

```bash
NODE=local-only/runtime/node-v24.21.0-darwin-x64/bin/node
$NODE --expose-gc tests/photo-cache-memory.mjs
$NODE --expose-gc tests/preferences-queue-memory.mjs
```

원본 측정 JSON과 최종 로그·지문은 로컬 `evidence/optimization-20261025/`에 보관합니다(Git 제외). 공개 저장소에는 합성 측정 스크립트와 이 요약만 포함할 수 있습니다.

## 적용과 남은 범위

실행 중 서버는 기존 코드를 메모리에 유지하므로 이번 변경이 자동 적용되지는 않습니다. 적용 시 [README의 업데이트 절차](../README.md#업데이트)에 따라 초안을 보관하고 로컬 세션 정리·정상 종료·재시작·새 입장·QR 로그인을 진행합니다. 에이전트가 사용자 연결을 자동 종료하지 않았습니다. commit·push도 수행하지 않았습니다.

Apple Silicon 실기기, 이번 변경의 Windows/Linux 네이티브 재검증, 실제 계정 장시간 사용·절전 후 복구·사진/읽음 등의 확인은 별도 범위입니다. 이번 결과는 기존 제품 구조와 프로토콜을 유지한 합성·로컬 통합 검증입니다.
