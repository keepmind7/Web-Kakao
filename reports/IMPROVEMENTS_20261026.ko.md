# 로직·저장·사진·방 전환 개선 (2026-10-26)

기준 커밋 `49b9997`과 [진단 보고서](DIAGNOSIS_20261026.ko.md)의 재현을 바탕으로 사용자가 지정한 일곱 항목을 수정했다. 체감 지연 구간은 **방 선택 후 메시지·사진 표시**다. 초기 로그인 시간을 줄였다고 해석하지 않는다.

현재 사용자 서버·로그인·기기·개인 설정·사진을 조작하지 않았다. 실제 로그인/읽음/발송·서버 재시작·커밋·push는 미실행이다. 아래 기능 검증은 합성 데이터·전용 임시 파일·주입 transport·실제 고정 SDK의 loopback·격리 Chrome에 한정된다.

후속 독립 진단에서 편집창 응답 격리와 별개로 **동일 방의 오래된 별칭 HTTP 요청이 최신 저장을 덮는 P2**가 재현됐다. 서버의 저장 순서 보호와 전체 초기화 경계는 [후속 별칭 수정](ALIAS_ORDER_FIX_20261026.ko.md)에서 보완했다. 아래 수치는 최초 일곱 항목 차수의 기록으로 유지하며 후속 검사와 합산하지 않는다.

## 설정 삭제와 실패 처리

명시적 `forget()`은 해당 계정의 정확한 `<account-hmac>.json.corrupt-<숫자>` 복구본도 개별 검증 후 삭제한다. 다른 계정·identity key·다른 이름의 파일은 보존한다. 설치 키 손상으로 계정의 저장 namespace를 신뢰할 수 없으면 삭제 성공으로 보고하지 않고 false/storageError로 거절한다. 여러 파일 삭제는 단일 파일시스템 트랜잭션이 아니므로 중간 실패 시 이미 끝난 개별 삭제를 롤백하지 않는다.

영구 저장을 끄는 것, 계정 초기화, 메모리 profile의 close는 기존처럼 다른 동작이다. 파일은 암호화하지 않는다. 같은 프로세스의 폴더별 직렬 큐64와 stale 검증을 유지하며, 별도 서버 프로세스 간 쓰기 잠금은 추가하지 않았다.

Windows 검사는 부모 상속 권한 변경과 새 파일의 기록 전후 보호를 확인한 범위다. 검사·기록 중 다른 프로세스가 ACL이나 경로를 계속 변경하는 상황까지 원자적으로 보호한다고 보장하지 않는다.

## 사진 취소 계약과 한계

- 새 서버는 `photoCancellation:true`를 광고한다. 이전 실행 서버가 이 기능을 광고하지 않으면 새 정적 UI도 기존 사진 URL/취소 방식을 사용한다. 이 호환 경로에 새 취소 보장을 소급하지 않는다.
- 새 사진 HTTP에는 로컬32hex 요청 ID가 붙는다. `POST /api/photo/cancel`은 기존 Host·loopback·헤더 세션·Origin·CSRF와 제한된 JSON 필드를 검사한다. 임의 원격 URL을 받지 않는다. 해당 ID의 room/message/index가 일치해야 한다.
- 취소가 GET보다 먼저 도착해도 tombstone으로 늦은 요청을 거절한다. registry는512개, 닫힌 ID는30초 후 정리하고 활성 응답은15초 수명 제한을 둔다. 인증/계정 종료의 정리와 소비자 취소를 연결한다.
- 취소한 slot은 서버 close ACK까지 보유한다. `clear()` 후에도 이전 예약을 보존하고 Web Locks 없는 환경도 진행+회수 중 요청 합계를 탭당2개로 제한한다. Web Locks 지원 시 논리 슬롯은 origin 전체2개다. 브라우저 요청·로컬 HTTP 응답·공유 상류 fetch는 서로 다른 수명으로 측정한다. 공유 상류 fetch는 기존4개, pending40, cache512개/30MiB 상한을 유지한다.
- 취소 ACK가2초 안에 확인되지 않으면 현재 loader 세대의 새 요청을 보류하고, 해당 요청 시작에서 최대30초까지 슬롯을 회수한다. 오류 callback 예외가 정리를 막지 않게 한다. 이 장애 회수 기한 자체가 실제 네트워크 close의 성공 증거는 아니다.

판정은 일곱 항목의 합성·계정 없는 로컬 통합 **검증 성공**, 실제 계정 회귀·다른 OS 실행 **미실행**, 과거 manifest 대조 **실패**로 구분한다. 실제 사용 적용과 속도 개선 폭이 남아 전체 제품 판정은 **부분 성공**이다. 정식 배포 품질이나 모든 과거 문제가 해결됐다는 판정이 아니다.

## 속도 해석과 남은 범위

합성 메타 gate가 닫힌 동안 선택 방 요청이 시작됨을 확인한 것이며 실제 카카오 화면이 몇 초 빨라졌다는 측정은 아니다. 이미 캐시한 방의 선택은 로컬 경로이므로 매번 외부 이력을 요청한다고 가정하지 않는다. 본문 DOM 재사용과 사진 지연 로딩은 기존 구현을 유지한다. manager의 방 비교는 중첩 검색에서 Map 조회로 줄였다.

초기 SYNCLINK→INFOLINK의6.5초 설정 예산과 Windows 계정 준비 helper 비용은 이번에 줄이지 않았다. 사용자 체감 구간과 다른 작업이며 오픈방/초기 읽음 계약을 확대하지 않았다. Windows 영구 쓰기는 보안 검사를 보강했으므로 검사 비용이 늘 수 있다. 안전 검사를 생략하거나 영구 성공 캐시로 속도를 얻지 않는다.

현재 방 목록500개·별도 개인 설정 파일의 방 설정500개 제한은 유지한다. 퇴출한 방의 저장된 별칭을 자동 삭제해 공간을 만드는 정책은 도입하지 않았다. 세션 Bloom은 재전송 증거를 보존하며, 재등장한 방의 과거 이벤트는 보수적인 partial 표시가 가능하다. 전체 과거 대화 보관을 새로 보장하지 않는다.

진단 D8의 비정상 숫자 필드 일반화, 장시간 사용·macOS/Linux의 이번 수정 실행, 실제 카카오 선택→본문/사진의 개선 폭은 미확인이다. 일반 숫자 변환이 실제 카카오 응답에서 문제를 일으켰다고 확정하지 않는다.

## 적용과 다음 확인

실행 중인 서버에는 파일 변경만으로 서버 모듈이 적용되지 않는다. 사용자가 준비됐을 때 README의 **초안 보관→로컬 세션 지우기→stop→start --gap-probe --messaging→open→QR 승인** 순서로 적용한다. 이번 코드 수정 요청을 재시작·새 로그인·읽음/발송 승인으로 확대하지 않았다.

다음 실제 관측은 기존 방의 캐시/처음 조회, 텍스트/사진, 단일/다중 탭, 빠른 방 전환으로 나눠 확인하면 된다. 본문·이름·사진 URL을 기록하지 않고 선택→첫 본문, 이력 요청, 사진 대기/표시의 단계 시간만 구분한다. 실제 읽음·발송 확인은 대상·횟수·영향을 별도로 정한 후 진행한다.
