# Web-Kakao 후속 작업 계획

2026-10-18 기준. 이 문서는 다른 PC의 clone에서도 읽을 수 있는 후속 계획이다. 현재 기능·제약과 검증 이력은 [README](../README.md), 역할과 배정 규칙은 [운영 문서](OPERATING.md)를 기준으로 한다. 비공개 진단 보고서·실행 장부가 없어도 이 두 문서로 새 계획을 만들 수 있어야 한다. 아래 실제 읽음·사진·이름·오픈채팅 단계는 실행 결과가 아니다. 모든 작업에 목표·입력·배타적 소유 파일·의존성·통과 기준·필요 자원 lease를 확정한 최신 패킷을 전달한다.

## 인수인계 상태

- 2026-10-18 최신 전체 합성 검증: Node369·Python67·FULL 격리 Chrome67 통과. 별도 instance4·서버 경계11·브라우저 경계39·Python API 부재 모의10도 통과했다. - 직접 발송 읽음 정책은 독립22개 중9개 기대 assertion 실패를 먼저 재현하고 구현 후22개·관련 회귀63개를 통과했다. 해당 차수 소스에서 새 전체 Node318개와 계정 없는 FULL 격리 Chrome51개 분류도 통과했다. 사진의 실제 SDK 암호화 loopback ns:false와 독립 helper 기본true, 비boolean 무전송, 거절/불명 무재전송·권한 무효화·잘못된 방 차단을 확인했다. 일반 조회 OFF·미리보기 취소·방 전환·중복 방지 회귀와 원본 UI 시안5개는 유지한다. Python·REA·ADB와 사용자8787·계정은 사용하지 않았다. 실제 모바일 배지 해제는 아래 사용자 재확인 항목으로 남는다.

- 최신 미읽음 배지 보고: 웹 발송 후 본인 모바일 채팅 목록의 해당 방에 빨간 미읽음 배지가 표시된다. 모바일 말풍선은 오른쪽 본인 글이며, 발송 당시 웹 읽음 동기화는 OFF였다고 사용자 확인했다. 사용자는 기존 상대 메시지도 읽음 처리될 수 있다는 설명을 듣고 **직접 보낼 때는 그 방의 읽음도 동기화**를 선택했다. 보완은 읽음 권한을 확인한 문자·답장의 WRITE noSeen:false, 사진 POST ns:false를 사용한다. 독립 upload helper는 readOnSend=false가 기본이며 직접 발송 session이 검증한 권한을 명시 전달한다. 일반 조회 OFF·미리보기·취소는 원격 읽음을 추가하지 않고 별도 NOTIREAD·추가 발송·불명 결과 재전송도 추가하지 않는다. 실제 모바일 배지 결과는 사용자 재확인 전까지 미실행이며 단독 원인은 미확정이다. 기존 own-target 하향/dedupe 경계는 이번 범위에서 바꾸지 않는다. 이전 직접 발송 읽음 차수는 Ctrl+F5 뒤 사용자 직접 대화 연결 끊기→다시 연결로 worker를 갱신했으며 현재 build8은 전체 서버 재시작을 따르고, 에이전트는 사용 중인8787·계정에 접근하지 않는다.

- 2026-10-17 분석용 Windows PC에서 카카오톡26.8.1.5315 native x86 PE32 설치본과 서명·원본/복사본 SHA-256 일치를 확인했다. 로컬 REA6.5.0·Ghidra12.1.4·JDK21, provider/MCP doctor와 합성 함수 분석이 통과했다. 실제 EXE의 리소스·Ghidra import·목록·진입점 디컴파일도 실행했으나 기능 경로는 미확보여서 정적 분석은 부분 성공이다. 함수33개 중 내부2개·외부31개, 정의된 문자열117개와 관련 패턴0건을 관측했다. Windows 준비·분석 실행기와 합성 검사24개·독립 검수를 완료했다. [PC 분석 안내](../tools/pc_analysis/README.ko.md)의 현재 결과와 한계를 따른다.

- 이후 APK 없이 기존 이름 없는 방의 제한적 CHATINFO 보완, 인증 사용 시점 만료, 기한 있는 로컬 API 요청과 복귀 갱신을 구현했다. 추가 QA에서 찾은 최초 방 선택·폴링의 이력 누락 경합도 수정했다. 새23개를 포함한 Node191개·격리 Chrome37분류가 통과했다. 실제 방 이름·절전·장시간 관찰은 미실행이며 실서버를 재시작하지 않았다.
- 읽음·사진 도착·오픈채팅 텍스트 도착은 후속 사용자 확인 사례에 한해 성공으로 갱신했다. 일부 방 이름·미확인 오픈채팅 사진/답장/읽음·큰 사진·장시간 동작은 남아 있다. 합성 성공과 실제 사용자 확인을 구분한다.
- 이전 분석 환경에는 카카오톡 APK가 없었다. 현재 PC의 위 입력에서는 정적 분석을 수행했으므로 후속 작업은 기존 근거와 해시를 확인하고 미확보 경로에 한정한다. 다른 clone에서는 도구·APK·사용권을 다시 확인하며 이 PC의 파일이 있다고 가정하지 않는다.
- Git으로 역할·스킬·계획 절차를 공유한다. 과거 대화·실행 중 세션·인증·분석 원본·발송 승인은 이전하지 않는다. 새 clone은 새 run을 만들고 필요한 실제 작업은 다시 대상을 확인받는다.

## 2. 사진 발송

analyst가 정확한 APK 또는 권한 있는 PC 설치본에서 업로드 연결·프레임·파일 바이트·COMPLETE·메시지 생성 경로를 추적한다. 분석 대상 버전·해시와 접속 프로필 차이를 남긴다. architect가 SHIP/POST 전후 실패와 결과 불명 경계, worker가 수정할 파일, QA의 정상/거부/소켓 종료/중복 기준을 제안한다. 기존 clientId+내용 해시, 무재전송 계약을 보존한다. 근거 없는 추가 WRITE를 하지 않는다.

APK에서 SHIP → V2SL/AES_GCM128 → POST → offset 이후 스트림 → COMPLETE/ChatLog를 확인했다. 후속 분석으로 h의 무필터 put, 명시 BSON null/int32/int64와 프레임 writer를 확보했다. build7은 s Long, ex:"{}", sp:null, scp:1, silence:false를 명시하고 제품의 보조기기 역할에 dt4를 적용한다. 현재 직접 발송 경로는 사용자 선택에 따라 검증한 읽음 권한을 helper에 전달해 ns=false를 사용하며 독립 helper의 기본 ns=true는 유지한다. 사용자가 보낸 시험 사진의 실제 표시는 확인을 받았다.128KiB 초과 사진과 다른 형식은 별도 QA로 구분한다. 계속 실패하면 수락/offset/바이트/COMPLETE/소켓 종료 단계를 대조한다. 필드 필수 여부·실제 서버 송신 한도는 미확정이며 추가 WRITE를 하지 않는다.

합성 media-wire/reply-upload와 Chrome의 선택·붙여넣기·미리보기·취소를 먼저 확인한다. 과거 실제 발송 6회 승인은 모두 소진됐다. 추가 발송은 새 대상·사진·횟수·영향 승인 후에만 한다. POST 수락·바이트 쓰기·COMPLETE·수신 기기의 실제 도착을 각각 기록한다. 사진이 수신 기기에 실제 표시되어야 해결이다.

## 3. 대화방 이름

기존 이름 없는 방도 CHATINFO로 보완하도록 구현·합성 검증했다. 최초 목록 이후 연결당 최대8개·직렬·방당1회이며 ID 일치 응답의 제목만 갱신한다. 별칭·멤버십·읽음 위치·이력·방 종류·발송 지원은 보존한다. 실제 단절은 종료하고 선택적 메타 오류는 건너뛴다. 원래 문제 방의 실제 이름을 대조한 상태는 아니다.

다음은 별도 승인된 실제 목록 확인으로 제목과 같은 방인지 대조하고, 남은 오픈링크/부분 참가자 이름의 근거를 조사한다. 개인 모바일의 제목과 서버 제목·웹 별칭을 구분한다. 이름 복구로 발송 가능 여부를 바꾸지 않는다.

## 4. 오픈채팅 지원

사용자 QA의 canContext까지 비활성인 현상에 대해 고정 소스의 INFOLINK 경로를 보완했다. 기존 known OD/OM의 missing link만16개/1회/2.5초, 요청집합·alias·revision을 대조하며 링크 활성화는 context만 먼저 연다. 본인 entry 검증 전 text/photo는 유지 차단한다. 실제 원격 동기화가 링크를 누락했는지는 미확정이다. 이후 사용자 QA에서 확인한 오픈방의 텍스트 작성·모바일 도착은 성공했고, 다른 오픈 기능과 조건은 별도 확인이 필요하다.

build7은 OD/OM을 보존하고 알려진 기존 방의 링크·context 본인 멤버·역할·활성 상태를 대조한 조건부 호환 구현이다. canText/canReply/canPhoto/canRead/canContext를 별도로 소비하며 unknown/정보 불명은 차단한다. 전체 privilege 표는 미확보이며, 실제 오픈채팅 텍스트 도착은 별도 사용자 확인 사례에 한한다. README의 사용자 QA에서 기능별 실제 표시와 비활성 버튼을 구분한다. 로컬 차단과 서버 거부를 구분하며 자동 가입·발송 시험은 하지 않는다.

APK에서 OD/OM, JOINLINK 필드, SYNCLINK cursor/응답, OpenLink 이름 우선순위 일부를 확인했다. build7에서 원래 종류·링크·본인 멤버 상태를 worker에 보존한다. 남은 문제는 호환 역할과 전체 privilege 제약의 차이, 실제 서버에서의 기능별 결과다. 기존 방 전송마다 JOINLINK를 호출하거나 OD/OM을 일괄 허용하지 않는다.

## 새 세션에서 재개

사용자가 Windows 분석 PC에서 이어받아 APK 분석과 build7 수정을 진행했다. 다른 PC에서는 실제 공유된 커밋을 clone한 뒤 아래 문서와 프롬프트로 시작한다. 이 PC의 미커밋 변경·실행 기록·인증·개인 설정·런타임·분석 원본은 Git clone으로 복원되지 않는다. 커밋·push는 별도 요청이 필요하다.

우선순위는 **확인된 읽음·사진·답장·오픈채팅 텍스트 동작 보존 → 사진 지연 측정과 기존 오픈방의 미확인 기능별 관찰 → 남은 실패 단계에 한정한 조사·수정**이다. APK 추출·서명·코드 분석과 근거 있는 수정은 진행했지만 기능 전체 해결은 미확인이다. 새 clone에는 비공개 원본·근거·런타임이 없으므로 다시 준비한다. PC EXE는 별도 진입점 분석에 머물렀다. 실제 계정 동작을 자동 시작하지 않으며 재개 시 현재 사용자 지시를 따른다.

새 역할·스킬이 현재 세션의 목록에 없으면 먼저 대상 디렉터리에서 새 세션을 시작한다. 전역 설정이나 권한 모드를 바꾸지 않는다.

```powershell
# 먼저 clone한 저장소 루트로 이동한다.
codex -C (Get-Location).Path
```

새 세션에 전달할 요청:

```text
$harness README.md, AGENTS.md, .harness/OPERATING.md와 .harness/FOLLOWUP.md를 읽어줘.
현재 build8의 구현·검증·남은 사용자 QA 범위를 먼저 정리해줘.
부모 cwd와 커스텀 역할 6개·프로젝트 스킬 발견을 확인하고,
작은 읽기 전용 커스텀 자식 하나로 실행 점검을 해줘.
이 PC의 런타임·고정 소스·APK가 실제 있는지 확인하고 새 run을 만들어줘.
사용자 요청 범위에서 합성 검사와 localhost 서버를 준비하고,
상대방 읽음1·사진 도착·기존 오픈방의 기능별 QA 항목을 알려줘.
로그인·기기 변경·실제 읽음·메시지·사진 발송은 자동 수행하지 마.
추가 제품 수정은 현재 사용자 지시와 근거에 따라 배정해줘.
REA가 필요하면 정확한 입력·사용권·독점 lease를 확인하고 정적 분석만 진행해줘.
APK가 없으면 Android 분석을 미실행으로,PC EXE 결과는 별도 근거로 유지해줘.
```

새 세션도 실제 생성 응답을 확인해야 하며 이 명령 자체는 성공 보장이 아니다. 과거 run이 없는 clone에서 기존 실행 재개를 시도하지 않는다. 준비가 된 후 최신 입력에 맞춰 APK·PC 정적 분석·공개 소스/합성 작업 중 가능한 범위로 새 run을 만든다. 다른 OS의 실행은 별도 검증 대상이며 현재 준비 도구·Chrome fixture는 Windows 사용을 기준으로 한다.
